# 0.7.48 Plan — Start Gifts: A Start-Gift Budget, Drawn Per Company (`#giftAll` / `#giftBot` / `#giftHuman`)

> **Roadmap position (Pre-FFT `0.7.*`, after fair-start modes `0.7.47`):**
> answers `drafts/new/game-options.md` (the second TODO of
> `drafts/map-fair-start-modes.md`). The start is a fixed grant today
> (`OrbitTech.starterGrant`: purse 6.00, starter ship, EMC-1 / SP-1 / BAT-1);
> this plan adds an operator-tunable gift budget drawn per company at start.
> `0.7.49` (radar) is the only pool entry this plan depends on, and it is
> gated so the two land independently.

Standalone spec: a fork can rebuild this from this file alone. Source note:
`drafts/new/game-options.md`.

## decisions (settled with the player)

1. **Budget, not a gift list.** Three sliders set the money: a base gift for
   all, an additional gift for bots, and an additional gift for human players.
   Each is `0` (default) … `20 cr`. The sum is previewed live.
2. **Every company draws.** Bots and the human each draw from their own budget
   (`bot = base + botAdd`, `human = base + humanAdd`), so a gift to the human
   also strengthens the rivals and stays balanced.
3. **Random 1+ gifts + rest cash.** Within the budget each company draws
   `1…GIFT_MAX` pool entries and keeps the remainder as cash (at 6 cr: FT-1 +
   2 cr).
4. **Science gift = a random science product** (research), not a fitted item:
   it unlocks a tech on a family ladder without fitting anything.
5. **Pool** = cash, a ship part (IMP / FT), a random science product, radar.
   The radar entry grants the `0.7.49` facility and is omitted until that plan
   lands.
6. **Determinism.** The draw comes from the career seed + company index: a run
   replays the same gift, a new seed re-rolls.
7. **Career only**, settings + URL params, no new sim or slot.

## problem

`resetCareer` applies one fixed `starterGrant` to every company. A fixed gift
table would be unbalanced across seeds and rosters, and a per-gift toggle
spreads the balance across many switches. A single **budget** keeps the balance
in one number the operator slides, while the pool stays a fixed, tunable table
(`balance_lab.html` can reprice it later). The gift must be a company asset
drawn once at start — not a per-flight effect — so it lives in the career, not
the ship.

## 1. the pool and the budget

```
GIFT_BUDGET_MAX = 20          // the slider ceiling, cr
GIFT_MAX = 3                  // max entries drawn per company (balance knob)
```

`GravityScene` carries the three sliders (default `0`):

```
giftAll, giftBot, giftHuman   // cr, 0..GIFT_BUDGET_MAX
```

`giftBudget(isBot) = giftAll + (isBot ? giftBot : giftHuman)`.

The pool is a flat table of `{ id, kind, value, weight, payload }`. `value` is
the cr-equivalent the draw stops at; `weight` biases the pick.

```
GIFT_POOL = [
  // cash — the remainder is cash anyway; these let a pure-money gift be drawn
  { id: 'cash2', kind: 'cash', value: 2, weight: 3 },
  { id: 'cash4', kind: 'cash', value: 4, weight: 3 },
  { id: 'cash6', kind: 'cash', value: 6, weight: 2 },
  // ship parts — owned and (for a fitted slot) put on the ship
  { id: 'ft1',  kind: 'part',  value: 4, weight: 3, payload: 'FT-1' },
  { id: 'imp1', kind: 'part',  value: 5, weight: 2, payload: 'IMP-1' },
  { id: 'ft2',  kind: 'part',  value: 6, weight: 2, payload: 'FT-2' },
  { id: 'imp2', kind: 'part',  value: 9, weight: 1, payload: 'IMP-2' },
  // science — a random science product (research), not a fitted item
  { id: 'sci',  kind: 'science', value: 6, weight: 3 },
  // radar — grants the 0.7.49 HQ facility (omitted until 0.7.49 lands)
  { id: 'radar', kind: 'radar', value: 6, weight: 1 }
]
```

The values are a starting table, not law: `balance_lab.html` reprices them and
the worklog records the final numbers. The pool is **data**, so a balance pass
edits one table, not the code.

## 2. the draw

`drawGifts(budget, seed, index)` — pure, deterministic, no allocation beyond the
result:

```
drawGifts(budget, seed, index) → { drawn: [gift…], cash: number }
```

- `rng = mulberry32(seed ^ (index * 2654435761))`;
- `remaining = budget`, `drawn = []`;
- if `budget < minPoolValue` → return `{ drawn: [], cash: budget }` (a budget
  below the cheapest gift is pure cash, no gift — still matches "1+ when it
  fits");
- loop up to `GIFT_MAX`: `candidates = pool.filter(g => g.value <= remaining)`;
  if empty, break; pick a weighted random candidate (no immediate repeat of the
  same `id`); push it, `remaining -= g.value`;
- return `{ drawn, cash: remaining }`.

`minPoolValue` is the smallest `value` in the pool. The draw is a **budget
spend**, not a count: a 20 cr budget may draw one expensive gift or several
cheap ones, which is the intended variety.

## 3. applying the gifts

`applyGifts(career, drawn, cash, budget)`:

```
career.ledger.purse += budget;                 // the whole budget is granted
career.giftSpent = 0;
for (const g of drawn) {
  career.ledger.purse -= g.value;              // the gift is paid out of the budget
  career.giftSpent += g.value;
  if (g.kind === 'part')    applyGiftPart(career, g.payload);
  if (g.kind === 'science') applyGiftScience(career, g.value);
  if (g.kind === 'radar')   career.radar = true;   // 0.7.49
  // cash: nothing — it is already the remainder in the purse
}
// `cash` is the remainder; it is already in the purse (budget − giftSpent)
```

- **cash** — no effect; the remainder stays in the purse.
- **part** (`applyGiftPart`): `ownPart(career, item)`; if the part's family is a
  fitted ship slot (`hold` / `engine` / `tank`) and the ship does not already
  carry a better one, set `career.ship[kind] = item` and recompute
  `career.ship.mass = OrbitTech.shipMass(career.ship, career.ship.cargoTons)`.
  No research charge — the gift owns it. `career.buildSpent += g.value`.
- **science** (`applyGiftScience`): pick a random researchable family and a
  rung within the gift's value, then `unlockPrototype(career, family, params,
  id)` + `OrbitScience.acceptHull(career.science, family, params, id)` +
  `career.research += 1` + `career.sciSpent += g.value`. This unlocks a tech
  (e.g. engine IMP-2 becomes known/buildable) **without fitting an item** — the
  player's "random science product for this money". The exact rung is picked
  deterministically from the seed so the gift is replayable; the value caps the
  rung (a 6 cr science gift cannot unlock a 9 cr rung).
- **radar** — `career.radar = true` (the facility itself is `0.7.49`'s; this
  plan only grants it).

`careerStats` gains `out.gift = career.giftSpent` so the money line stays
readable: `purse = starter + gift − property − science + profit − running`.
`career.giftCredit = budget` records the granted total for the trace.

## 4. where it is applied

`resetCareer` already copies the grant into the ship, pad and purse. After the
grant, before the first flight:

```
const isBot = career.index !== PLAYER_INDEX;
const budget = giftBudget(isBot);
if (budget > 0) {
  const { drawn, cash } = drawGifts(budget, career.seed, career.index);
  applyGifts(career, drawn, cash, budget);
}
```

- The **human** company draws from the human budget; each **rival** draws from
  the bot budget in its own `createCareer`/`startCareer`. The draw is per
  company (seed + index), so companies differ without a shared roll.
- `career.giftDrawn = drawn.map(g => g.id)` is stored for the trace and replay.
- A restart is a new company: `resetCareer` re-draws from the new seed.

### URL and records

`?gift=`, `?giftBot=`, `?giftHuman=` set the sliders on boot; `syncSeedUrl`
writes them back. The three values and the drawn gift ids go into the run
record and replay link (`encodeLink`), so a replay re-applies the same gifts.

## 6. tests

New `experiments/gift_test.js`:

1. **Default:** all sliders 0 → no draw, `purse` 6.00, no part/science/radar,
   `giftSpent` 0.
2. **Budget 6, human only:** the human draws ≥ 1 gift, `purse = 6.00 + 6 −
   sum(non-cash values)`, remainder is cash, `giftSpent` = sum of values.
3. **Determinism:** same seed + index → same `drawn`; a different seed → a
   different draw (over a seed sweep).
4. **Per company:** with `giftBot` set, every rival draws from the bot budget
   and the human from the human budget; counts match the company count.
5. **Part gift:** an `FT-1` draw marks it owned and fits it on the ship
   (mass recomputed); no research charge.
6. **Science gift:** a science draw unlocks a prototype (a tech becomes
   `knownGear`) and raises `career.research`, without changing the ship fit.
7. **Sub-minimum budget:** a budget below the cheapest gift → `drawn` empty,
   the whole budget is cash.
8. **Radar gift (with 0.7.49):** a radar draw sets `career.radar`.
9. **No frame cost:** the draw runs once at start; nothing in the step loop.

`dom_smoke` once at the end: the three sliders exist, default 0, the preview
line updates, and a career started with a gift shows the drawn gift in the
career drawer/trace.

## scope boundary

No gift editor; the pool is a fixed, tunable table. No per-gift toggles — the
three sliders are the only controls. Radar as a gift requires `0.7.49`. No
gifts outside career. No randomization beyond the draw; no allocation in the
frame path. The gift is a start-time company asset, not a per-flight effect.
