### Important verified difference: API expansion

I loaded the current and fetched modules separately:

- `GravityGame`: **328 → 440 enumerable keys**
- `GravityBot`: **18 → 95 static keys**
- `CommsCopy`: unchanged at **22 keys**

The new exports include scratch buffers, caches/accessors, tuning constants, and internal helpers—not just a part manifest.

That simplifies extraction and retains many bare internal calls, but makes implementation details externally reachable. It conflicts directly with `0.7.53`’s exact-key requirement.

## Good ideas to borrow from the commit

### 1. Several boundaries are better than the proposed broad files

`0.7.53`’s `game_ship.js` combines wear, repair, fuel, research, prototypes, statistics, radar, and construction. Its `game_flight.js` also includes the launch book.

The commit offers useful separations:

- `game_ship.js`: wear, repair, fuel
- `game_build.js`: construction, parts, radar
- `game_science.js`: research and prototypes
- `game_book.js`: launch history
- `game_departure.js` versus `game_legs.js`
- `bot_route.js` versus `bot_rivals.js`
- `bot_trace.js` separate from setup and policy

**Those are distinct reasons to edit a file**, not merely smaller line counts.

I would not automatically adopt every boundary: the five-file seat solver has substantial shared dependencies, and the bot’s launch/burn planning remains distributed. Smaller files alone do not prove better task locality.

### 2. Mechanical extraction and a declaration audit

The strongest execution idea is the scope-aware extraction:

- assign complete top-level statements by anchor;
- detect cross-file mutable reads and reject cross-file writes;
- reject definition-time reads of unavailable declarations;
- audit that each original statement occurs exactly once.

This is stronger than “cut contiguous blocks, run syntax checks.” Keep the audit reproducible rather than relying only on a worklog claim about a discarded tool.

### 3. A structural split test

The commit’s `parts_test.js` checks load order, imports, duplicate publication, and unresolved namespace references.

Borrow the **invariants**, adapted to private `K` hooks and attachment functions. Its regex implementation is useful scaffolding, not a complete scope/dependency proof.

## What to retain from `archive/0.5-plan-gui-split.md`

The enduring ideas are:

- **Index before moving:** banners and routing already reduce reading cost.
- Move declarations by **complete statement anchors**, including their comments.
- Keep state, scratch buffers, and algorithms with their owner.
- Prefer a cohesive larger file over an arbitrary line limit.
- Keep hot loops together.
- Separate structural moves from cleanup.

Do **not** reuse its flat-global mechanism for game/bot modules. Both newer approaches correctly account for CommonJS consumers and name collisions.

Also, treat the old GUI plan as design intent rather than proof that its size targets were achieved: the current repository instructions explicitly retain broadly shared state in the composer instead of forcing artificial ownership.

## Problems to fix in `0.7.53` before implementation

### 1. Specify late binding explicitly

The attachment design is sound, but **earlier parts cannot destructure later-registered hooks**:

```js
const { refitShip } = K; // permanently undefined if registered later
```

Use definition-time destructuring only for already-available dependencies; resolve forward dependencies at call time through `K` or the public target. The commit makes this distinction explicit; the plan should too.

### 2. Finish specifying the comms assembly

The proposed core loads first, but its engine reads tables supplied by later parts. The plan must define:

- how those tables are accessed without capturing `undefined`;
- when exports from later parts are installed;
- who finalizes/freezes the complete object.

Having `comms_topics.js` freeze the entire module couples a content file to assembly. Prefer core-owned finalization.

### 3. Tighten the API claims

“Byte-identical public API” is stronger than equal `Object.keys`.

The browser-only, non-enumerable `_part` still changes own-property inspection and leaves an attachment entry point. Either explicitly permit it or remove it after assembly.

Likewise, the listed “~20” game kernel hooks actually amount to roughly fifty. Inventory them before promising a tiny kernel.

### 4. Replace guaranteed locality percentages with measurements

The proposed 85–92% savings and universal 1–2-file task claims are estimates. Follow the GUI plan’s better acceptance idea: try representative real edits and measure which files must actually be understood.

## Recommendation

Revise `0.7.53`, rather than cherry-picking the commit wholesale:

1. Keep **private `attach(Target, K)` parts** and fresh per-instance closures.
2. Adopt the commit’s clearest domain separations—not necessarily all 30 parts.
3. Add explicit early/late dependency rules and assembly finalization.
4. Require a mechanical move audit plus browser/Node structural checks.
5. Preserve exact API checks and the existing fresh-VM fixture.

**Validation performed here:** module loading and enumerable API comparison only. I inspected the commit’s recorded test results but did not rerun its behavioural suites.
