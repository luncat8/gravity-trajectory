# 0.3.1 — game mode `max route`: a trajectory with no length limit

Standalone spec: a fork can build this from this file alone. The mode rewards a
single shot's **route length** and removes the 60 s horizon, so the prediction
has to be computed in slices instead of one call.

## 1. the problem with the present prediction

`GravitySim.predict` is one synchronous call with four independent limits:

| limit | value | consequence |
| --- | --- | --- |
| `MAX_STEPS` | 7 350 | 61.25 s of flight — the pre-launch horizon slider (5…60 s) sits inside it |
| `PATH_MAX` | 28 900 points | 240.8 s at `DT = 1/120`, then points are dropped silently |
| `BUDGET_MS` (`budgetMs`) | 10 ms | `END_TRUNCATED` — the path stops where the frame budget ran out |
| `FLY_HORIZON` | 240 s | in-flight continuation, already at the point wall |

Measured on seed 31 at t+07:00, 26 static bodies, full trace to the horizon
(this build, node, no budget cut):

| horizon | static field avg / worst | moving ports avg / worst |
| --- | --- | --- |
| 60 s | 2.24 / 8.24 ms | 3.68 / 7.61 ms |
| 120 s | 4.15 / 4.84 ms | 8.16 / 10.05 ms |
| 600 s | 16.98 / 18.88 ms | 33.35 / 39.19 ms |

`advance` alone is 7.5 ms per 72 000 steps (≈ 0.10 µs/step for 26 bodies), so a
600 s static trace is ~17 ms and a 1 800 s one ~50 ms; moving ports are ~2×.
**A 1 800 s trace is a fifth of a second — too slow for a mouse-move, perfect for
a sliced job.** That is the whole reason this mode is cheap to add.

## 2. rules

- Same physics, same world, same fixed `DT`, same launch bases, same gravity
  editing as the existing game mode.
- A flight ends only on **impact**, **leaving the field**, **abort**, or the
  route wall (`ROUTE_SECONDS = 1800 s`, 216 000 steps). There is no horizon
  slider and no time cap.
- The aim's trajectory is computed **to its end** — the player sees where the
  shot lands before firing, however long it is.
- Score: **systems visited**, then **route length** (sum of the flown paths in
  px, larger is better), then **fewer shots**, then **less flight time**.
  Length as a ranker rewards a long sweeping tour rather than straight hops;
  systems stay first so the mission is still the grand tour.
- The whole run is still a pure function of `(seed, rate, shots)`, so replays
  keep verifying.

## 3. the sliced tracer

Refactor `traceProbe` into a resumable job and keep the current call as a thin
drain loop, so every existing caller and bench behaves exactly as before:

```
job = gravity.routeBegin(origin, angle, speed)   // spawn + snapshot field, clear the job state
while (gravity.routeStep(job, steps, deadline)) {}  // returns false when finished
                                                     // (impact / exit / wall)
```

- `routeStep` runs at most `steps` physics steps and stops at `deadline`
  (`performance.now()`), returning `true` while work remains. It re-uses
  `probe`, `stepX/stepY` and the `pred*` arrays — no allocation per call.
- **Point stride follows the buffer.** When the point buffer fills, compact it
  2:1 in place (exactly what `recordTrail` already does for the trail) and
  double `pathStride`. 1 800 s then needs 216 000 / 32 = 6 750 points.
  Target: `pathStride = 1 << ceil(log2(steps / PATH_MAX))`, recomputed when the
  buffer compacts, and never above 32.
- **Budget per frame**: 4 ms of tracer work in `frame()`; the flight continues
  to be interactive. A 1 800 s static trace finished in 5 frames, a moving-port
  one in 9; the common case (< 120 s) finishes in one or two.
- **Aim edits restart the job**, but the last finished path stays on screen,
  dimmed, with `computing 43 %` in the readout — no blinking, no freeze.
- **Launch is enabled only for a finished job**; pressing enter while the job
  runs drains it synchronously first (bounded by the route wall), so a link or
  a bench never records a half-computed shot.
- The in-flight continuation keeps `FLY_HORIZON = 240 s` for the *drawn* path
  (it is redrawn ahead of the cargo anyway); the recorded route length comes
  from the live integration, not the drawing.

## 4. score and readouts

- `route length` in the HUD switches to the mode's score: the finished path
  length of the armed shot, then the flown total across shots.
- A new `route` stat shows `1 830 px · landing P14 · 41.2 s` for the armed shot
  and `best route` for the run.
- End of run: `route 12 480 px · 26 / 26 · 4 shots · 96.4 s`.

## 5. replay link

- `encodeLink` gains an optional `rule` parameter, `tour` when absent:
  `#game=1&seed=31&rate=3&rule=route&shots=…&end=…`
- `decodeLink` accepts `rule` in `{tour, route}` and rejects anything else. The
  end step count may reach 216 000 — `END_FORM` already allows 9 digits.
- Rules that differ between modes (cap seconds, abort limit, score order) are
  read from one table keyed by rule, not scattered through the GUI:
  `RULES = { tour: { cap: 14400, score: … }, route: { cap: 216000, score: … } }`.
- A route link opened from a tour build (no `rule` support) fails the version
  check; bump the link `FORMAT` to `2` only if a tour link would otherwise
  verify wrong under the route build — measured: it does not, so keep `1` and
  treat an unknown `rule` as invalid.

## 6. acceptance

1. `experiments/route_bench.js` (new):
   - a sliced trace equals a one-shot trace point for point (`pathStride = 1`,
     identical end reason, end point and length) for 200 random shots;
   - the point stride policy keeps memory flat: a 1 800 s trace stores
     ≤ 28 900 points and finishes with `pathStride ≤ 32`;
   - a 600 s trace run 8× 1/60 s slices per frame never exceeds 4 ms per slice
     (worst of 48 shots), and a whole trace is ≤ 45 ms of work;
   - `routeBegin` allocates nothing (same array references before and after).
2. `game_bench` gains a route run: play 3 shots in route mode, copy the link,
   replay at ×1, ×8 and skip — identical end state and `verified ✓`.
3. `dom_smoke`: switch to route mode, aim, assert `computing` then a finished
   path with `pathStride = 1`, launch, and the HUD shows route length.

## 7. risks

- **Long flights make the trade clock run a long way.** The world clock advances
  with the flight field time; 1 800 s of flight at rate 3 is 90 sim minutes,
  about a fifth of the 7 h warm-up. That is intended (colonies age on the route)
  but it means a route run is not comparable to a tour run's colonies. Both are
  seeded, so comparisons inside a mode stay fair.
- **Repel-heavy gravity editing** can keep a probe alive for the full wall; the
  wall is the answer, and `END_WALL` is a new end reason shown as `route wall`.
- **Drawing cost**: 28 900 points at stride 4 in `drawPrediction` is 7 225
  segments per frame. Measured budget is fine (the current draw already strides
  to 4 above 6 000 points); keep that code path and add the 30 s markers.
