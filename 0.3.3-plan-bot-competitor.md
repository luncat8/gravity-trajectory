# 0.3.3 — bot competitor

Standalone spec. The bot flies the same seeded world under the same rules and
produces a score to beat. It is deterministic from `(seed, rate, rule,
difficulty)`, so it never has to be stored in a link.

## 1. two ways to compete

| form | cost | what the player sees |
| --- | --- | --- |
| **ghost run** (recommended first) | one search per bot shot, run in the background after the player's shot lands | the bot's trail drawn as a dim second line, a scoreboard row `bot 18 / 26 · 3 shots` |
| **live race** | the same, but the bot launches while the player is aiming | a shared world where each system pays only its first claimant |

The ghost run reuses everything that exists: the replay machinery already flies
a recorded shot list, the codec already ships it, and the score already ranks
runs. Build the ghost first; the live race is a presentation of the same
decisions with a turn order.

## 2. the decision

For the current base (the landed planet, or a fixed opening list at run start)
enumerate a polar grid and score each candidate with the existing
`GravitySim.predict`:

- angles: 24 (normal), 48 (hard), offset by half a step to avoid the axes;
- speeds: `[120, 180, 240, 300]` px/s (`[150, 250]` on easy);
- search horizon: 20 s (normal), 30 s (hard), 12 s (easy).

**Measured** (seed 31, t+07:00, 26 static bodies, page in node): 96 predictions
at a 20 s horizon = **283 ms**, ≈ 2.95 ms each including the path writes. A
4 ms-per-frame job therefore makes a normal decision in ~70 frames (~1.2 s of
wall time) without touching the frame budget, and ~0.3 s if drained in one go
(acceptable for the bot's own turn of a ghost run).

Score:

```
score = 10 · newVisits           // the mission
      +  6 · (landed ? 1 : 0)    // a landing is what enables the next shot
      +  1 · predVisits          // revisits still cross a system
      -  0.25 · predTime         // do not dawdle
      +  0.001 · predLength      // prefer the longer, more interesting route
```

`newVisits`, `predVisits`, `predTime`, `predLength` and the end reason all come
straight from `predict()`, so the bot sees exactly what the human sees. A
candidate that leaves the field scores `-Infinity` unless nothing else is
available.

Hard difficulty adds a **1-ply continuation**: take the predicted landing point,
freeze the field at the landing field-time, re-trace up to 8 candidate angles
from that planet, and add half of the follow-up's `10·newVisits`. The frozen
field is an approximation — the ports will have moved by the time the second
shot really starts — and the plan says so in the help text. Cost: 8 extra traces
per candidate is too much (48 × 8 = 384 traces ≈ 1.1 s), so hard prunes to the
best 4 first shots, then continues: 4 × 8 = 32 traces (~0.1 s).

## 3. determinism

- No `Math.random`, no wall clock inside the decision; ties break on
  `(angleUnits, speedUnits)` so two machines pick the same shot.
- Candidate traces must run on the **same** `fieldT` and roster the human would
  get; take the snapshot once per decision (`snapshotField`) and restore it
  after, exactly like `predictFlight` does with `savedStepX/Y`.
- The bot never edits gravity and never changes the rate. Under `rule=route` it
  uses the sliced tracer from `0.3.1`: `routeBegin(origin, angle, speed,
  ROUTE_SECONDS)` + `routeStep(4)` per frame, so a decision is a background job
  rather than a stall, and the search grid stays short — only a finalist is
  traced to the end with `predictFull`.

## 4. money mode

In `0.3.2`, the bot pays the same 1.00 per launch and must stop when the purse
cannot cover it. Its scoreboard row shows systems and purse left; the run ends
when it cannot launch. It uses the same `earn()` function as the player, so the
economy is not duplicated.

## 5. presentation

- **Trail**: the bot's flown path in dim ice-blue, drawn by the existing trail
  renderer from a ghost buffer (the bot's own `GravitySim` instance, stepped
  with the same `DT`; it does not touch the trade clock — it flies on its own
  field copies, so the world is unchanged).
- **Scoreboard**: one line under the score, `bot · 14 / 26 · 4 shots · 1 232 px`,
  updating as the bot lands.
- **Thinking indicator**: `bot thinking 43 %` in the same line, from the job's
  progress counter.
- **After the run**: `bot finished 26 / 26 in 6 shots` and a `copy bot link`
  button that emits the ordinary replay link for the bot's shot list — useful
  as a challenge to send to another player.

## 6. difficulty table

| level | angles × speeds | horizon | continuation | expected |
| --- | --- | --- | --- | --- |
| easy | 16 × 2 | 12 s | no | 12–18 systems, 8–14 shots |
| normal | 24 × 4 | 20 s | no | 22–26 systems, 6–10 shots |
| hard | 48 × 4 → prune 4 | 30 s | 1-ply, 8 angles | 26 systems, 4–6 shots |

The greedy chooser already used by `game_bench` reaches 26 / 26 in 6 shots with
a 60 s horizon and a much larger grid, so the hard level is expected to be
close to that; the table is a target to measure, not a promise.

## 7. acceptance

1. `experiments/bot_bench.js` (new): the same decision twice on the same state
   is identical; a normal bot completes a full tour on seeds 7/31/913 within the
   shot budget; the decision fits in ≤ 0.4 s of CPU for normal and ≤ 1.2 s for
   hard; the candidate loop allocates nothing per candidate.
2. `game_bench`: a bot ghost run's shot list, encoded and replayed, reproduces
   the bot's own end state (`verified ✓`).
3. `dom_smoke`: ghost trail appears, scoreboard text updates, the bot's own turn
   ends at a landing, no frame-budget overrun (`autoInterval` stays 1).

## 8. risks

- **Search cost on moving ports** doubles (measured 2× per trace), so the job
  budget must be per-frame, not per-decision.
- **Frozen-field lookahead** is an approximation; it can pick a follow-up that
  is impossible once the ports move. Keep the 1-ply term small (half weight) so
  it never outweighs a real first shot.
- **Ghost world drift**: the bot must not advance the shared `tradeSim`; give it
  its own `GravitySim` and let the GUI draw its trail from that instance.
