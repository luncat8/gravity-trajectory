# 0.6.7 plan — a trajectory you can read without seeing it

Standalone spec: a fork can rebuild this from this file alone. Source note:
`drafts/sound-and-photos.md` §7.1 ("think how blind people could play and think
about trajectory"). Depends on the flight HUD (0.5.17) and the existing aim
sound.

## problem

The note asks a design question, not for an audio feature: *how would a blind
player hold a trajectory in their head?* The page answers that with pixels in
four places — the aim line, the predicted-trajectory drawing, the planet pills
and the scoreboard — and with sound in one (the aim bus). The sound is already
good at **direction and distance**; what it cannot carry is the *plan*: where the
shot ends, what it visits, what it pays, why the launch is blocked.

So the first step is not more sound. It is making the text the page already
computes reachable without sight, and then letting the sound annotate that text.

## 1. the readout (text first)

One live region, `#srStatus` (`role="status"`, `aria-live="polite"`,
visually-hidden), fed by **one** function `srAnnounce(text)` on a throttle
(at most one announcement per `1.2 s`, and only when the text changed):

| when | the line it says |
|---|---|
| a shot is armed | `P4 to P7, 13.0 s, 3 systems, +1.80, lands` |
| the armed shot is blocked | the rail's own reason (`cap 48 < 61 px/s`) |
| landed | `landed P7, purse 4.20, fuel 30 kg, next: load at P7` |
| a scan finished | the helper's notice verbatim (`quest shot · P7 · +2.00`) |
| the clock is paused | `paused · N s` (only on the transition) |

Every string is built from values the aim line, `railBlock` and the helper notice
already compute — the plan forbids a second pricing path, so the readout cannot
disagree with the screen (the 0.5.15 rule applied to text).

- The canvas gains `role="img"` with a `aria-label` naming the mode and the ship
  state; the interactive aiming **stays pointer-only** in this plan (keyboard aim
  is §3).
- The flight HUD's existing groups get `aria-labelledby` on their group labels,
  and the state tag (`landed P# / coasting / burn armed`) is the region's short
  summary, so a screen reader landing on the panel hears the state first.

## 2. the sound annotates the readout

The Voronoi aim channel already carries heading and distance. Add **two** cues
that map to the readout's words, not to new physics:

- **the landing**: when the trace completes, a single arrival tone on the
  destination's note (the trajectory synth already does this in flythrough;
  `voronoi` gets the same one-shot), so "it lands" is audible without the text.
- **the block**: when a launch is refused, the existing EMC beacon's `blocked`
  branch (`emcKnown && !emcReady`) distinguishes *rail too weak* from *no rail*
  by two pitches. That is one more branch in `emcBeacon`, no new voice.

## 3. keyboard aim (explicitly deferred, with the shape written down)

A blind player cannot drag. The cheapest full keyboard path, recorded here so a
later plan does not re-invent it:

- `tab` selects the aim target among the bodies the HUD's `work` rows name (a
  cycle, not a grid);
- `←/→` turn by one snap unit (`2^-20` turn), `↑/↓` change speed by one snap
  unit (`2^-10 px/s`), `shift` for ×1/20;
- `enter` arms, the existing `enter` fires.
- It is **not** in this plan because it needs the keymap owned by one file
  (`gui_aim.js`) and a focus model the page does not have; the readout above is
  the prerequisite either way.

## Validation

- `dom_smoke`: arming a shot fills `#srStatus` with the same numbers the aim line
  prints; a blocked shot says the rail's reason; a landing says the next work;
  no announcement repeats when nothing changed; the throttle holds under a drag
  storm (a synthetic 200-move drag produces one announcement, not 200).
- `sound_test` / `trajectory_sound_test`: the arrival one-shot fires once per
  completed trace and the two block pitches are distinct.
- No new allocation in `draw` or in the aim update path: the announcement
  strings are built only on a change, never per frame.
- `game_bench`, `career_bench`, `bot_bench` unchanged.

## Scope boundary

No keyboard aiming (see §3), no change to how anything is *priced*, and no
rewriting of the sound generators. The page becomes describable before it
becomes playable without sight; that order is the plan's main decision.
