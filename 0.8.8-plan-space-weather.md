# 0.8.8 Plan — Career Space Weather

## Goal and scope

Add space weather to **career mode**: high-wear regions, regions that reduce
or disable ship observation reports, a viewable weather overlay, an expensive
advanced observation device that resists interference, and weather sources on
corrupted and rebel planets. The design comes from `drafts/map.md` and
`drafts/new/observation-device-OBS-1.md`. Other modes remain unchanged.

This is a design and validation plan, not a fixed balance specification. The
motion comparison and the decisions below must be resolved before gameplay
implementation; numbers, overlap rules and the advanced device's specifications
are not yet approved. The prototype does not change the game rules.

## Existing contracts

- `GravityGame.careerWearAt(career, x, y)` currently returns 1.
  `careerWeatherWear` adds only the extra wear after a live flight step;
  `careerAdvance` already charges base flight wear. Do not charge it twice.
- Ships report through their fitted OBS; `visitReports` also respects quiet
  planets and special Capital/A.R.F. behavior. Reporting collects visit value
  and affects corruption. `GravitySim.stepInsideAt` and `markSystemsAt` use
  fixed planet-orbit ellipses; prediction, flight ledger and stay-pay rely on
  entry/inside records. A reduced report range is not merely a visual filter.
- `orbit_tech.js` currently has OBS-0 and OBS-1. A higher-tier device needs
  actual research, shop, ownership, refit, mass and pricing integration;
  it is not just a drawing or a flag.
- Existing forecasts price base wear from duration. Weather-dependent wear
  needs a path and time; predictions, bots and the launch book must not claim
  exact parity while ignoring it.

## 1. Compare motion and appearance first

Build a small local visual experiment for the same seeded maps and elapsed
world time: slowly drifting 2D noise, evolving noise sampled through a third
coordinate, and a combination of drift and evolution. Compare both wear and
observation fields, including a moving rebel debris source and a stationary
planet jammer. Use the same inputs and colour scales for each candidate;
inspect the ordinary bounded map and, when available, the periodic torus and
its seams. The prototype must not mutate the game or decide balance.

Choose the motion separately for each effect after comparing readability,
smoothness, repeatability, seam behavior and measured cost. Record the chosen
motion and parameters in this plan before implementing the gameplay field.

## 2. Resolve gameplay rules before implementation

The human notes specify the features but not enough to select these values:

- **Fields:** coverage, scale, speed, intensity and how overlapping sources
  combine; maximum wear multiplier and how a report range can reach zero.
- **Jammer:** a planet above 50% corruption has a chance to install one;
  settle the chance, when it is evaluated, its area and lifetime, what happens
  if corruption falls, and how its requested 4× range reduction combines with
  weather and the advanced device.
- **Rebel debris:** specify the chance and interval in simulation time, wind
  direction, extent, lifetime and accumulation limit. Do not use render-frame
  counts: pause, playback speed and skip must not alter outcomes.
- **OBS-2 or equivalent:** price, mass, research/unlock and exactly how much
  resistance it provides; whether its nominal clear-weather range differs
  from OBS-1. The notes suggest about 20% more range, not a fixed decision.
- **Entry and landing:** define range sampling at the ship/planet, entry when
  a moving field changes while the ship is already nearby, landing at a planet
  whose report range is disabled, and interaction with stay-pay and Capital /
  A.R.F. rules. Preserve bribe, quiet-planet and rot semantics deliberately.
- **Forecast:** define what the player and bots can know about future weather
  and planet events. If future events are not predictable, label estimates as
  such rather than representing them as guaranteed live outcomes.

## 3. Implementation contracts

- Use seeded, simulation-time-based weather and planet events, independent of
  drawing, browser frame rate and actor iteration order. One shared world owns
  event state; all companies sample the same weather at the same world step.
  Account for moving planets and the periodic minimum-image geometry after
  `0.8.0`. No changes to gravity or ship trajectories themselves.
- Apply the wear multiplier through the existing wear path to human, bot and,
  when `0.7.45` is present, fleet flights. Preserve the wear-scale control and
  the no-weather baseline. Update wear forecasts and repair reserves using
  the same path/time model or explicitly label the forecast limitations.
- Separate geometric system visits from OBS report eligibility if needed:
  changing OBS range must not silently change non-career scoring or gravity.
  Use one reporting-range rule for live accounting, predictions, helper/bot
  evaluations and the displayed OBS area. Preserve the existing collision and
  landing rules; handle the chosen landing/report rule explicitly.
- Add a weather view option showing distinguishable wear and interference
  fields and planet sources. It reads the same weather state as gameplay and
  cannot affect the simulation. Keep overlay updates bounded and avoid
  per-frame allocations; measure with large maps and multiple ships.
- Seeded starts, saves, replay and skip need the same weather state and event
  history, including mid-flight and between-flight restoration. Extend their
  existing formats as required and test them; never rely on a redraw to advance
  weather. Document any deliberate save-format change.

## 4. Verification

- Unit tests for field sampling, reproducible planet events, 50% corruption
  boundary, 4× jammer range, overlapping sources, source expiration and OBS
  resistance once their rules are decided. Test still air and periodic seams.
- Flight tests for baseline and increased wear, scale zero, OBS inside/outside
  the changed range, disabled reports, landing and stay-pay, quiet planets,
  special worlds and worn-out/unfitted devices. Compare live flight with
  prediction, helper and bot estimates under the documented forecast model.
- Equal seeded outcomes across normal and skipped play, different frame
  cadences and save/replay restoration; repeat for multiple careers and fleet
  ships sharing a world. Other game modes retain their current behavior.
- Browser check that the overlay toggle and displayed OBS area follow the
  sampled state, do not mutate it and remain usable with a large roster.
  Benchmark frame slices and bot planning against the pre-weather baseline.
- Run the relevant wear, OBS, politics, replay, bot and page checks listed in
  `AGENTS.md` and report results; use `git diff --check` and `node --check`
  for touched scripts.
