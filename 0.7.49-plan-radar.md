# 0.7.49 Plan — Radar: An HQ Facility That Reveals Every Ship's Landing (`career.radar`)

> **Roadmap position (Pre-FFT `0.7.*`, after `0.7.48`):** answers
> `drafts/new/radar.md` (the first TODO of `drafts/map-fair-start-modes.md`).
> Radar is a **company facility built at the HQ for money** — not a ship part,
> not a tech unlock. The HQ sees the whole map and sends the data to the ship,
> so one build reveals, for every ship, a ghost icon on its predicted
> trajectory with the time to its next landing. `0.7.48` may grant radar as a
> start gift; this plan is the facility itself.

Standalone spec: a fork can rebuild this from this file alone. Source note:
`drafts/new/radar.md`.

## decisions (settled with the player)

1. **Radar is an HQ facility.** Built at the HQ for money, any time; no ship
   slot, no mass, no per-ship fitting.
2. **Company-wide.** The HQ owns it and broadcasts to the ship, so one build
   covers the whole map for the owning company.
3. **Reveal = trajectory + landing time.** For every ship (own and rivals), a
   ghost icon on its predicted trajectory, labelled with the time to its next
   landing (`+35 s` on his, `+41 s` on mine).
4. **Cost 6 cr**, balanced for mid-game — between EMC-1 (builds at 3.04) and
   EMC-2 (7.83) — so a company builds EMC-1 before radar.
5. **Requires an HQ** (`career.hq >= 0`); a space-start company builds it once
   it settles an HQ.
6. **Bots use it to avoid collisions**: a radar bot de-prioritises landing on a
   planet another ship is heading to, just profited from, or captured.

## problem

Ship-fitted devices (`OBS`) are per-ship and per-visit, and there is no
company-level information asset. A global ship-tracking reveal needs something
that persists independent of the ship, is bought once, and is owned by the
company — so the **HQ** owns it. Building it at the HQ for money fits the
existing pad/facility model (`fitPad`, `career.buildSpent`) and keeps the ship
light. The reveal reuses the prediction machinery the aim trace already uses
(`GravitySim.predictFlight` → `predX`/`predY`/`predCount`), so it costs no new
physics.

## 1. the facility

```
RADAR_COST = 6               // cr, mid-game
```

`career.radar = false` on creation; `resetCareer` clears it (a restart is a new
company, no radar). The build gate is a pure predicate:

```
canBuildRadar(career) → bool
  careerRule() && career.ended === CAREER_OPEN && career.hq >= 0 &&
  career.at === career.hq && purse >= RADAR_COST
```

`buildRadar(career, trade)`:

- refuse unless `canBuildRadar`;
- `career.ledger.purse -= price(career, RADAR_COST)`;
- `career.buildSpent += RADAR_COST`;
- `career.radar = true`;
- one comms/notice line `radar built at HQ` (reuse the existing notice path).

No pad change, no ship change, no new planet. It is a boolean company flag plus
the spend — the cheapest possible facility.

## 2. the reveal

`radarShips(out, humanCareer, world)` fills a caller-owned array (no per-frame
allocation). For each ship the human company can see — the player's ship and
every rival's ship — it produces one record:

```
{ x, y,       // current position
  predX, predY, predCount,   // predicted path (reused buffers where possible)
  landStep,   // the step the ship lands, or -1 if it never lands in the horizon
  tLand }     // (landStep - liveSteps) * DT, seconds to landing; 0 if parked
```

- **flying ship:** run a bounded prediction on its `sim`
  (`predictFlight(RADAR_BUDGET_MS)`) and read `predX`/`predY`/`predCount` and
  the landing step. `RADAR_BUDGET_MS` is a small, fixed budget (the same class
  as the aim trace) so the reveal never stalls the frame.
- **parked ship:** `predCount = 0`, `tLand = 0`, position = its planet.
- **own ship included** — the draft's `+41 s on mine`.
- The reveal is **global** (the HQ sees the whole map); there is no range
  limit. It reveals predicted trajectories only — no hidden state beyond what a
  trajectory implies.

The prediction is the ship's own `predictFlight`, so the ghost matches what the
ship will actually do (same field, same steps). The result is memoised per
`(fieldStamp, shipStep)` so a static field does not re-predict every frame.

## 3. the UI

### the toggle

A `radar` checkbox in `#viewBar` (same row as `full view` / `clean render`),
**enabled only when the human career has radar**:

```
<label id="radarLabel" class="viewCheck" title="career only · show every ship's
predicted trajectory and time to landing (built at the HQ)">
  <input id="radarView" type="checkbox"> radar</label>
```

- Off by default even when built (the operator chooses to look); the checkbox
  is the view, the facility is the asset.
- Disabled + a tooltip when `career.radar` is false.

### the ghost icons

Drawn in the world layer (`gui_draw_world.js`), reusing the prediction path:

- for each ship from `radarShips`: a translucent ship marker (the owner's
  colour, lowered alpha) along `predX`/`predY`, and at the landing point a ghost
  icon with the time label `+N s` (or `landed` when `tLand <= 0`).
- the own ship is drawn the same way — its `+41 s` label is part of the reveal.
- the path is a thin line, distinct from the aim trace and the trail, so the
  radar reads as an overlay, not a new flight.

## 4. bots use radar

A rival whose career has radar reads other ships' predicted landings when it
picks a launch. This is a **scoring refinement**, not a new sim: the bot reuses
the same `radarShips`-class prediction.

In the launch candidate scoring (`careerNextShot` / `careerScoreFacts`), add a
radar penalty to a destination's score when:

- another ship's predicted landing lands on that planet within
  `RADAR_HORIZON` (`tLand` within the horizon) — the bot avoids sitting where a
  rival is heading;
- the planet was **just profited from or captured** by another ship (the
  existing visit/claim state) — the bot avoids a stale prize.

The penalty is a fraction of the landing's value (a balance constant
`RADAR_AVOID`), so radar shifts the bot's choice without overriding a clearly
profitable landing. Bots without radar keep today's scoring exactly. This is
the draft's "wait and look where other players move to not sit on the same
planet".

## 5. interaction with 0.7.47 (starts)

- **Planet start:** the HQ exists from the start, so radar can be built
  immediately (subject to the 6 cr).
- **Space start:** `hq = -1`, so `canBuildRadar` is false until the company
  lands and settles an HQ; after that it builds normally. This is consistent
  with the universal no-HQ evacuation rule (`evacTarget`).
- **Capital start:** also `hq = -1`; radar is available once an HQ is settled,
  the same as space start.
- The radar gift from `0.7.48` sets `career.radar` directly and skips the build
  (and the spend), so a gifted radar works in any start that has an HQ.

## 6. tests

New `experiments/radar_test.js`:

1. **Build gate:** at the HQ with ≥ 6 cr → builds, `purse − 6`,
   `career.radar` true; away from the HQ / in flight / < 6 cr / `hq < 0`
   refuses.
2. **Reveal:** with radar, every flying ship yields a predicted path and a
   `tLand > 0`; a parked ship yields `tLand = 0`.
3. **Own ship** is in the reveal with its own `tLand`.
4. **No radar:** `radarShips` returns an empty list; the view checkbox is
   disabled.
5. **Determinism:** the ghost's landing step equals the ship's own
   `predictFlight` landing (parity).
6. **Bot:** a radar rival de-prioritises a planet another ship is heading to
   (the score penalty applies); a rival without radar scores it unchanged.
7. **No frame cost:** the reveal memoises; no allocation per frame.

`dom_smoke` once at the end: the `radar` checkbox exists, is disabled without
the facility, and toggling it draws ghost icons on the predicted trajectories.

## scope boundary

No per-ship radar; no radar outside career. Radar is a live-career facility, not
a replayable historical event (the flag is on the career, not the shot). No
range limit — the HQ sees the whole map. No new physics: the reveal reuses
`predictFlight`. The bot penalty shifts choices; it does not give the bot
information the human does not also see.
