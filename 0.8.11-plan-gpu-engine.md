# 0.8.11 Plan — GPU Engine (WebGL Field Build, FFT & View Rasters)

> **Roadmap position (`0.8.*` · Engine work, no rule changes):** Lands after
> `0.8.0` (periodic FFT solver + grid views) and `0.8.10` (classic precalculated
> field grid) exist, and fits anywhere after the `0.8.3` calibration — it changes
> no law, no balance and no gameplay surface, only where grids are computed and
> where rasters are painted. It also serves `0.8.8` (space-weather overlay raster)
> and `0.8.4`–`0.8.6` not at all: those read sampled state, not renderers.

Standalone spec: a fork can rebuild this from this file alone. Source note:
`drafts/new/gravity-precalculate-trade-trajectories.md` §GPU engine:

	## GPU engine

	plan to implement WebGL engine - if available then:
	precalculated field and FFT can do on GPU if these modes selected. and better resolution.
	also view modes and space weather.

## 0. decisions

1. **GPU builds field grids; the CPU integrates.** When the engine is enabled
   and WebGL2 is available, the `0.8.10` classic force grid and the `0.8.0`
   periodic FFT solve (`Ax`, `Ay`, `φ`) run as GPU passes and are **read back
   once per snapshot** into the same Float32 arrays `fieldAt` already samples.
   Sample, `advance`, prediction, bot and helper code are untouched. No
   per-step, per-frame or in-flight GPU physics — the grids are precalculated
   by definition, so the GPU only replaces *who computes the snapshot*.
2. **The CPU is always the complete game.** Without a context, without
   `EXT_color_buffer_float`, or with the engine off, every path is exactly
   today's CPU path. The engine is an accelerator and a resolution upgrade,
   never a requirement; a machine that never sees WebGL2 plays the same seeds.
3. **Soft testing, CPU-only for physics.** All existing and new physics,
   career, replay and bench tests run the CPU path and remain the contract.
   The GPU gets compile-and-run smoke checks only (context created, programs
   linked, one pass rendered, readback finite, no GL errors) that skip cleanly
   when no context exists — headless CI never exercises a GPU. Pixel judgement
   is the user's; `findings-pitfalls-skills.md` documents the headless
   Chromium route for screenshots when a visual check is wanted. Rationale:
   SwiftShader-style software GL in a sandbox is a large, flaky harness that
   proves little; «compiled and working at least somehow on GPU» plus user
   verification is the honest bar for an optional accelerator.
4. **Field-build mode is run identity.** `cpu | gpu` joins the field snapshot
   identity (next to topology, dimensions and the precalc flag) and is carried
   by `&gpu=1` in the link/replay/saved-map codecs the way `&fft=1` is. A
   replay made under `gpu` restored on a CPU-only machine falls back to CPU
   with a visible note in the replay banner (the topology-mismatch pattern) —
   float rounding differs between builders, so the mode that built the run's
   field rides with the run instead of pretending parity. Default benches,
   tests and shipped links never carry `&gpu=1` and stay CPU.
5. **Better resolution is a recorded geometry.** The GPU may build the classic
   grid finer (e.g. 512² at `dx ≤ 5 px`); resolution is part of the snapshot
   geometry identity and of `&gpu=1`'s recorded state, so a GPU run and a CPU
   run of one seed are different fields by identity, not by accident. The
   periodic FFT grid keeps `0.8.0`'s geometry contract (powers of two from the
   world size); the GPU implements the same math at the same or finer power of
   two, recorded the same way.

## 1. the option

One checkbox in the experimental panel, beside `precalc field` / `periodic
FFT`:

	gpu engine

- Requires a WebGL2 context with `EXT_color_buffer_float` (float render
  targets); the checkbox probes on first open and darkens with a tooltip when
  the capability is missing. `file://` friendly — no extension beyond that one
  is required, no fetch, no worker.
- On: field snapshot builds run on GPU when the mode they serve is selected —
  the `0.8.0` FFT solve for periodic worlds, the `0.8.10` grid fill for classic
  `precalc field` runs. Toggling rebuilds the snapshot (and restarts the seed
  mid-run like any identity switch); replays lock it.
- The `0.8.9` arc shooter and every probe adopt the built snapshot through the
  existing sharing contract — the GPU result is just another immutable
  snapshot with `builder: 'gpu'` in its identity.

## 2. what is built on GPU

New file `gravity_gpu.js`, classic script, `module.exports` guarded, loaded
after `gravity_fft.js` / `gravity_grid.js`:

- **Context module.** One lazily created WebGL2 context shared by build passes
  and view passes; capability probe (`EXT_color_buffer_float`, max texture
  size, max varyings) recorded in the module; context-loss handling follows
  `gravity_field.js`'s existing lost/restored pattern, falling back to CPU
  builds until restored.
- **Classic grid fill.** The body-loop shape `gravity_field.js` already ships
  (uniform body array → per-pixel force) rendered into a float texture at the
  target cell resolution and read back into the snapshot's `(ax, ay)` arrays.
  Body counts beyond the classic shader's 48 uniform slots use a texture
  holding body positions/strengths — the torus rosters need this anyway.
- **Periodic FFT.** A fragment-pass radix-2 implementation (log₂ passes over
  row/column half-turns) computing `0.8.0`'s exact transform contract —
  unnormalized forward, single normalization on the inverse, DC bins of
  `kAx` / `kAy` / `kPhi` zeroed, minimum-image kernel sampled at the same
  `dx, dy` — into `Ax`, `Ay`, `φ` textures read back to the snapshot grids.
  `GravityFFT` stays the reference implementation and the CPU fallback; the
  GPU path plugs in behind the same solve entry point.
- **Readback discipline.** One `readPixels` per snapshot build, into
  preallocated buffers; no readback ever in the frame loop; build timing
  reported next to the CPU build timing in the bench log.

## 3. what is painted on GPU

- **Field/potential views.** `0.8.0` §6's CPU 256² offscreen blit and
  `gravity_field.js`'s CPU raster move to GPU passes when the engine is on:
  the snapshot grids upload once per snapshot (not per frame), the palette
  (hue = direction, lightness = `|a|`, the signed potential ramp, the zone
  colours) is the same GLSL table the shaders already share with the JS
  palette, and «better resolution» applies — the raster runs at canvas
  resolution instead of a quarter-size offscreen. Every view keeps its CPU
  fallback path unchanged; the view never samples the GPU asynchronously
  ahead of gameplay (it reads the same snapshot the physics reads).
- **Space weather overlay (`0.8.8`).** The weather/interference fields render
  as one more GPU pass over the same state the CPU overlay samples — same
  seeded weather state, same colours, CPU fallback intact. `0.8.8`'s contract
  (overlay reads state, never mutates it) is unchanged; this plan only moves
  where its pixels come from.
- **Torque/roster ceilings.** View passes bound their per-frame uploads: one
  texture per snapshot change, none per frame, measured with large rosters
  (`0.8.8`'s overlay benchmark and `gravity_bench`'s frame budget apply).

## 4. testing policy

- CPU contract: every test tier runs unchanged and CPU-only; `&gpu=1` never
  appears in shipped links, benches, saved maps or fixtures.
- `experiments/gpu_smoke.js` (**new**, skipped without a context): creates the
  context, links every program, runs one classic fill and one small FFT solve
  at 64², asserts finite readback and the loose analytic checks — kernel
  oddness (self-force ≈ 0), DC removal, round-trip relative error ≤ 1e-3 on a
  single-mode field — and one view pass with no GL errors. Assertions this
  loose catch wiring and indexing mistakes without pretending to be a parity
  harness.
- `dom_smoke` gains: the checkbox exists, darkens without a context, and the
  tag carries `gpu` when on; view toggles still work with the engine on.
- Visual verification checklist (user, recorded in the worklog): field view
  and potential view at 192 bodies, weather overlay on a corrupted/rebel map,
  seams on the torus, a `&gpu=1` replay restored on a CPU-only machine shows
  the fallback note.

## order

1. Context module + capability probe + smoke test skeleton (skips headless).
2. Classic grid fill on GPU behind `&pg=1&gpu=1`; snapshot identity carries
   the builder; CPU build untouched and still default.
3. View passes (field, potential) with upload discipline; CPU fallbacks pinned
   by existing view tests.
4. Periodic FFT on GPU behind `&fft=1&gpu=1` with the loose analytic checks;
   `GravityFFT` cross-checked on the 64² smoke grid by the user on a real
   browser once.
5. Weather overlay pass (`0.8.8` state), `&gpu=1` codecs, replay fallback
   note, README, one `dom_smoke` pass, user visual checklist in the worklog.

## Validation

- `experiments/gpu_smoke.js`: green wherever a context exists, skipped (not
  failed) headless; programs linked, passes drawn, readback finite, loose
  analytic bounds within their tolerances, no GL error state after a frame.
- CPU tiers all green and unchanged — `classic_physics_test`,
  `gravity_seed_test`, `gravity_bench` / `career_gravity_bench` / `bot_bench`,
  view tests: nothing in the shipped default path moved.
- Identity: `&gpu=1` round-trips through link, replay hash and saved map; a
  `gpu` replay restored without a context shows the fallback note and runs
  CPU; benches never carry the flag.
- Perf, reported in the worklog: GPU vs CPU build ms per snapshot (classic
  fill, FFT solve at 256²/512²), view frame cost at 26 and 192 bodies,
  readback size, retained GPU memory. The engine ships regardless of whether
  the numbers win — it must merely not lose badly, and the CPU path must not
  regress by a byte.
- `node --check` on every touched script, `git diff --check`.

## Scope boundary

No per-frame or per-step GPU physics; no GPU game logic; no worker, no fetch,
no build tooling. No new view modes — existing rasters move, nothing is added
beyond the weather overlay pass `0.8.8` already specifies. No parity harness
for software GL; no pixel-diff tests. No requirement that WebGL2 exists — the
CPU game is always complete. No change to sampled laws, seeds, benches or the
`0.8.0`/`0.8.10` numerics contracts; the GPU produces another builder of the
same snapshots, recorded as such.
