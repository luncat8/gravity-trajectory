# 0.7.6 plan — balance knobs, separate from the clock

Open. The clock pass (`0.7.1`) left one rule behind: **the game has one clock,
game seconds, and nothing on screen multiplies it**. What the player can still
want is to move the *balance* — how fast a pad charges, how fast rot grows, how
fast a visit pays — without lying about time. Those are different knobs and
they need their own plan.

## why not the old slider

The background `rate` slider used to be exactly such a knob by accident: pads
and the political clock ran on `steps · DT · rate`, so ×12 charged a pad twelve
times faster and rotted a world twelve times faster than ×0.5. It was labelled
as an animation control, sat in the background panel, and silently re-priced the
economy — the worst of both. 0.7.1 pinned the pads to `SUN_SEC_PER_GAME_SEC` and
the politics to `gameSeconds`, so the slider is now decoration.

## what a balance knob has to be

A knob that moves the balance must be:

1. **named as balance**, in the same panel as the other balance experiments
   (`experimental`, next to `g field` and `catapult ×`), never as a clock;
2. **declared in the label with its own unit** — `panels ×`, `rot ×`, `pay ×` —
   never in seconds;
3. **measured against the bench**: every balance knob gets a `career_bench` row
   that pins the default reading and a `career_bot_bench` run at each end, so a
   knob cannot silently become the new balance;
4. **one number**, applied where the law lives, not where the label reads.

## candidates, in the order they are worth having

| knob | where it multiplies | what it changes | risk |
|---|---|---|---|
| `pads ×0…×4` | `careerAdvance`'s `padSeconds` | charge and leak together, so a pad's *shape* holds | a ×4 pad nearly deletes the battery tier as a cost; the bot's `careerPadGear` yield moves with it, so it must read the same factor |
| `rot ×0…×3` | `advancePolitics`'s `seconds` | the grace, the passive rate and the epoch together | the epoch is an int; a ×3 rot must scale `REBEL_CHECK_SECONDS` too or the roll rate changes |
| `pay ×0…×2` | `planetProfitAtStep`'s age | how fast a visit's payout regrows | the pill prices a *rate*, so the HUD's `+0.00625/s` text is derived and must follow |
| `wear ×0…×3` | 0.7.2's `WEAR_SPACE` | ship ageing only | none until wear ships |

The first three share one shape: each is already a single age multiply inside
one function, so each knob is one factor at that call site plus one row in the
`experimental` panel. They belong in one pass, after `0.7.2` (wear) so the panel
is opened once with all four rows.

## what must not become a knob

- **The pace** is the player's watching speed, not a balance lever, and it
  already exists as `play ×N`; a balance knob that also sped the clock would
  reintroduce exactly the two-in-one that 0.7.1 removed.
- **The background animation** stays decoration. If a future feature wants the
  sky to matter (weather, a station closing), it becomes its own `map.md` layer
  with its own law, not a multiplier on the sky.
- **The wait's span** is 60 game seconds. A shorter or longer wait is a
  different feature (`0.7.5`'s evacuation trip already prices real time).

## open question a plan must answer first

Where do the knobs' values live — a URL param per family (`&pads=2`) so a shared
run is reproducible, or session-only so a link never carries a cheat? The
existing `g ×` and `catapult ×` are session-only and a link does not carry them;
a balance knob that a bench run must reproduce probably has to ride the URL.
