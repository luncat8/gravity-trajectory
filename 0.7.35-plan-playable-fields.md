# 0.7.35 plan — designed gravity fields the game can play

Standalone spec: a fork can rebuild this from this file alone. Source notes:
the integration list in `map-generator-helper.htm` (`save result to pre-generated
saved maps`, `to game add dropdown to select specific saved pre-generated map`).
The helper page, its roster editor, `map_gen.js` and `map_fields.js` already ship
(`archive/0.7.35-map-helper-worklog.md`); this plan is the one open item — the
game cannot yet play a field the helper designs.

## what ships today

- `planet_gravity.js` owns the seeded field: `gravity(seed, planet)` on
  `MIN = -1 … MAX = 3.5` in `STEPS = 20` (0.05) with a bias that thins the heavy
  middle (0.6 … 2.8, strength 0.3). `gravity_game.js` re-exports it as
  `planetGravity`, `PLANET_GRAVITY_MIN/MAX/STEPS`.
- Every reader goes through that one function: the page's field
  (`attachWorld` → `planetBaseStrength`), the career rules (`deep`,
  `fragile`, `HQ_GRAVITY_MAX` candidates) and the opening search
  (`openingPrepare` fills `openingStrengths` from it, specials and forced homes
  pinned to 1).
- The helper page designs a roster and writes `map_fields.js`:
  `{ v: 1, kind: 'field', name, universe, mass, gap, seed, rows: [{g, m, count}],
  gravity: [0.05-grid values], note }`. `GravityMaps.pick`/`gui_maps.js` never
  look at it, and no record is playable.
- Saved maps (`saved_maps.js`) are seed + universe + a seat plan proven by
  `prepareCareerStarts`; `?map=<index|name>` injects the plan and skips the
  search, and the saved-maps group has a picker (`mapPick`) that boots one
  specific record instead of a random one.

## problem

A designed field is the shape the generator *should* produce, and `map_fields.js`
is where it is written down, but there is no path from it into a run. The gap is
one function: the field a run reads is computed from the seed alone, so a design
can be compared against the generator (the helper does that) and never be played.

## design

**One override, in the one place every reader already reads.** A field is armed
with the seed it belongs to, and the draw returns it:

```js
// planet_gravity.js
function arm(values, seed)   // copy and snap 1..PLANETS finite values
function disarm()            // back to the seeded draw
function armed()             // snapshot { values, seed, tag } or null
function tagForSeed(seed)    // field identity for this seed, or an empty string
function seededGravity(seed, planet) // always the original draw
function gravity(seed, planet)      // field when armed, original otherwise
```

- The override is seed-keyed and falls back to the seeded draw beyond its
  length: the opening code examines all `PLANETS`, even for a small universe.
  The loader must validate that the field has exactly `universe` values before
  arming it. A seed alone is not a run identity: every transition to a seed-only
  run, including one with the same seed, must explicitly disarm.
- The tag encodes the exact grid-index sequence, avoiding hash collisions. It
  joins **all three** opening caches: `seatPlanKey` (including resumed searches),
  `careerOpenings`, and `openingTracks`. Each depends on the field, not just the
  seed. The helper's original-seed panel and baseline call `seededGravity`, so
  they cannot accidentally display an override.
- The page arms the field **before** anything reads a strength: in
  `startGame`, before `attachWorld`, `pinCareerStrengths` and
  `prepareCareerStarts`. Everything else follows from `planetGravity` — the
  field, the colours, the bot's probes, the seat search, `deep`/`fragile` rules —
  so there is no second list of gravities to keep in step with the first.
- Specs and HQs stay pinned to g 1 (`pinCareerStrengths`, `openingPrepare`),
  unchanged: a designed field describes the worlds, not the companies.
- The helper currently permits roster totals over `OrbitWorld.PLANETS`; refuse
  such saves with a clear message rather than silently truncating a design. The
  loader must also reject malformed or mismatched records before mutating state.

**The record.** `kind: 'field'` is the start record's fields plus the design, and
it may carry a proven `seats`/`targetPay` when the generator planned them:

```js
{ v: 1, kind: 'field', name: 'field 7 · 13 planets', seed: 93293, universe: 13,
  gravity: [...13 values], rows: [...], mass: 10, gap: 220,
  rule: 'career', bot: 'normal', player: 'user', cheat: null,
  rate: 1, gs: 1, fs: 1, ws: 1, ht: false, note: '...' }
```

The helper writes the record without `seats`; `make_saved_maps.js` gains a
`FIELDS=` mode that arms each field record, plans its seats with the same
`prepareCareerStarts` the page calls, refuses a field whose plan is not fair
(the existing `accepted` rule) and writes `seats` + `targetPay` back. That keeps
the registry's promise — every committed start record is the plan the search
returns — while the helper stays a design tool and never pretends to prove one.

**Loading.** `saved_map.js` grows `applyField(record)` → `PlanetGravity.arm`
(`disarm` for every other kind, so a seed run after a field run is clean), and
`startMapRecord` calls it before `startGame`. A field record without `seats`
still boots: the search runs on the armed field (~3 s) and the notice says
`saved map planned its opening`, or refuses with `no fair opening in this field`
when the design leaves fewer than one light landing per company.

**The address.** A seed link cannot reproduce a field, so `syncSeedUrl` keeps
`map=` for a field record instead of rewriting it to `seed=` (the rewrite is what
makes `?map=3` a seed link today). `?map=<name|index>` already resolves; a field
record stays a map boot for its whole life, and the page tests keep the address
of their own field record.

**The picker.** `gui_maps.js` labels a field record `· field` beside `· run`, so
the dropdown added in 0.7.35 selects it like any other saved map. No new button.

**Replays.** A replay hash carries the field it was flown on
(`career_replay`/`share` already snapshot `field.planets` for a restored run);
replaying a field run on a seed-only page must arm the field from the hash or
refuse, not silently fly a different map. One check in `career_replay_test`.

## validation

- `map_gen_test`: a designed field arms, reads back planet for planet, and
  disarms; a seed run after a field run reads the seeded draw again (byte-equal
  strengths to a fresh page).
- `saved_map_test`: a field record boots at its own gravities (the page's
  `planetBaseStrength` equals the record), its HQs are still g 1, and a
  `?seed=` boot after it is untouched; a field with `seats` skips the search, one
  without plans it and says so.
- `career_start_fairness` / `career_start_seat_test`: unchanged on seeds (no
  field armed) — the run's own check that the override leaks nowhere.
- `make_saved_maps.js --check` plus `FIELDS=1`: every field record is still the
  plan its field returns.
- `dom_smoke` once: the picker lists a field record and `load map` boots it.
- `node --check` on every touched file, `git diff --check`.

## scope boundary

No new planet kinds, no change to the geometry or to the trade world's seed
stream, no second gravity list anywhere: a field is data in the same registry
and the same draw. The helper stays the editor; this plan makes its output
playable. Distribution *balance* — whether a roster should ship as the default
generator shape — is the open question of `0.6.8-plan-seeded-map-opening.md` §3
and is not decided here.
