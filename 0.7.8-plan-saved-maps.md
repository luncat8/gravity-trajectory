# 0.7.8 plan — saved maps: a proven opening on disk, and an exact run state

## problem

A career page load spends almost all of its time in one place: the fair-opening
search. `prepareCareerStarts` traces candidate homes (`openingTraceHome` →
`GravitySim.routeDrain`) and ranks seamings, so one 13-world, 3-seat page load
costs ~33 s of a ~37 s boot in `node` on the 2-core sandbox. A page test pays
that before its first assertion, and the same search runs again for every seed a
test or bench samples.

The search is a **pure function** of `(world seed, trade seed, universe mask,
seat count, gravity/force scales, specials on)`, and the page asks for the same
answer twice per click (the scoreboard plans, `startGame` rebuilds). A proven
answer is therefore cacheable data, not code: seed + universe + `homes` +
`targetPay` fully describe a start map.

The second ask is the player's own: save the current run and continue it later,
from an initial map or from the exact state.

## design

One data file, one logic file, one GUI area:

| file | owns |
|---|---|
| `saved_maps.js` (root, loaded first) | the registry: `root.SAVED_MAPS = [record, …]`, or `module.exports` under node. Generated by `experiments/make_saved_maps.js`, and rewritten by the game's save action |
| `saved_map.js` | `GravityMaps`: record capture, seat-plan injection, exact-state pack/unpack, `fileText`, `download` |
| `gui_maps.js` | the four buttons in the run panel, the `?map=` boot path, status text |

Load is **just the predefined file name**: `index.html` carries
`<script src="saved_maps.js">`, so a saved map is available without a picker, a
network call or a build step. Save is **append and download**: the action
appends the record to the in-memory list and downloads the whole regenerated
`saved_maps.js` (Blob + `<a download>`); dropping that file over the repo's copy
is what makes the map permanent.

### the record

```js
{
	v: 1, kind: 'start', name: 'seed 2 · 13 planets · 3 seats',
	seed: 2, universe: 13, seats: [0, 7, 6], targetPay: 12.34,
	rule: 'career', bot: 'normal', player: 'user', cheat: null,
	rate: 1, gs: 1, fs: 1, ws: 1, ht: false,
	stats: { weakest: 0.71, sites: 3 }
}
```

`kind: 'run'` adds `state`: the exact snapshot (below). Every field the page
needs to reproduce the world and the opening is present; nothing is derived at
load except the world itself (seed-driven, ~1 ms).

### loading a start map

1. The boot path (`?map=<index>`) or the `load map` button arms the record.
2. `startGame` runs with the record's seed, rule, bot level, player count,
   universe, rate and experiment scales.
3. `startCareerRun` calls `GravityMaps.applySeats(…)` **before**
   `prepareCareerStarts`; a matching record injects its plan through
   `GravityGame.rememberSeatPlan`, which fills the existing seat-plan cache
   under the same key the search would use. The search never runs.

A record is used only when seed, universe, seat count and scales match, so a
stale file cannot seat a different world.

### saving an exact state

`kind: 'run'` stores what a continuation needs, captured only while every ship
is on the ground (a flight in the air is not saved; the button says so):

- the start map fields (so `startGame` rebuilds the same world and seats);
- the trade clock and world play state: `t`, the event queue, ports, ships,
  colonies and the random stream position (`OrbitWorld.seedRandom` exposes
  `getState`/`setState` for exactly this);
- the shared market arrays, the galaxy statistics and the run counters;
- every company — purse/ledger, ship fit and condition, pads and gear, owned
  parts, prototypes, science hull, task board, launch book, contract, stats;
- each rival's turn state (gap, plan, route, burn bookkeeping) and each sim's
  visit history.

Derived data is not stored: world geometry, turret phases, `launchPads`,
`planetCount`, `planetMask` and the field are rebuilt from the seed and the
universe, and gear is stored by id (`EMC-2`, `HOLD-8`) and relinked to the
`OrbitTech` tables so item identity survives.

Restore = `startGame(record)` then overwrite the live objects in place (never
replacing `game.career`, `tradeSim` or the market, which the GUI closures hold).
The round-trip test proves it: two pages are advanced from the same state, one
continuing, one restored, and their captured states must still match after 120
frames.

## generated start maps

`experiments/make_saved_maps.js` samples seeds per configuration, keeps the
first seed whose plan the page itself would accept
(`openingGroupAccepted`: no company without a site, distinct sites, every site
exitable, weakest pay ≥ 55 % of the best) and writes `saved_maps.js`. The
committed file carries one map per default-shaped configuration:

| universe | seats | count | why |
|---|---|---|---|
| 13 | 3 | 2 | the career default (YOU + normal rivals) |
| 13 | 2 | 1 | YOU + one rival |
| 26 | 3 | 1 | the old default subset, three companies |
| 8 | 2 | 1 | the small universe |
| 26 | 4 | 1 | the crowded universe |

Six records, 2.7 KB in total. The seeds are the first accepted one from an offset
(`from` in `CONFIGS`), not from 1: a per-config fresh start otherwise picks seed 1
every time, because the first world is the first one that passes.

## tests

- `experiments/saved_map_test.js` (fast tier, ~30 s): start-map records are tiny
  and load into the same seats the planner produced; a run captured at rest and
  restored into a fresh page continues identically for 240 frames at 8× speed
  (purse, clock and every captured array); `fileText` round-trips through a node
  `require`.
- A page that boots `?map=0` reports the saved seats and a boot time (~0.3–0.6 s
  vs ~37 s for a planned seed) — printed, not asserted, so a slow machine cannot
  turn a real win into a red test.
- `dom_smoke` once: `index.html` gained scripts and buttons; it now also checks
  the registry, the record shape and the six map elements.
- `PLANNED=1` in the same test boots the page on a seed and compares the planner's
  own seat list with the saved record: seeds 1 and 2 match, so the file is what
  the page would have chosen.

### what an exact save has to carry

The first restore attempt looked identical at the moment of restore and drifted
40 clock steps later. Capturing only the world was not enough; the page itself
holds state that decides the *next* frame:

- the sim's flight status, trail, origin and end reason (`relocate` resets all of
  it to "parked on the pad", but a career at rest sits on `STATUS_ENDED` with the
  trail of the flight it just finished);
- the bot's YOU-as-bot turn state (`bot.careerPlayer`: the plan it already made,
  its `readyStep` and the gap counters) — without it the bot re-plans on the
  first frame and queues its turret shot ~400 steps later than the live run;
- the leftover step accumulator (`playAcc`) and `playerBotSyncNeeded`, so the
  restored page does not replay the current frame.

All four are in the record now (`planner`, `page`, plus the ship keys) and the
round trip is exact.

## scope boundary

No new map generator, no change to the fairness law or to the seat search: a
saved map is what the current search already accepted. Exact saves cover a run
at rest; a flight in progress, a queued turret shot and a replay are not
snapshotted (the save button refuses while flying). Rival AI is restored from
its live turn state, not from its history log.
