# 0.7.4 plan — max distance from start

Standalone spec: a fork can rebuild this from this file alone. Source note:
`drafts/flight-lab-and-modes.md` §1.2:

	new game mode and sport competition: max distance from start. in this mode measure not trajectory length but distance from start, same start planet, long map in x direction - add planets until mode end, by default map is periodic in this game mode. land on planet cause finish for this player. variant of this game mode only EMC | EMC+allow imp1+big preinstalled fuel tank. variant: need to return back and land on same starting planet so strategy is to reserve at least half of fuel or precalculate all route that probably need to implement planner of imp burn in some future trajectory pos. similar like KSP planner work.

and the answers already given to its questions:

- **distance is the farthest path point**, not the landing point;
- **the map grows in x** by about 2–4 normal screens; x-wrap is the FFT map,
  the non-FFT map is a long strip with no wrap;
- the ship may return from either direction;
- career gets these as generated sport rules; the mode row gets the two
  variants:
  - `EMC & farthest path point & return`
  - `allow IMP & land far`
- the KSP-like burn planner and the “relaunch” variant are deferred.

Depends on the world/sim shape in `orbit_world.js`/`orbit_sim.js`, the camera in
`orbit_view.js`, and the career ship in `0.7.2` for the return variant's fuel.

## 1. what is measured

One accumulator per ship, not a new path buffer:

	GravitySim.startX/startY   // the start planet's core at launch
	GravitySim.farthest        // max px from startX/startY over the path
	GravitySim.farthestX/Y     // where that point was
	GravitySim.farthestStep

`spawn` sets `startX/Y` to the origin planet's core (not the 8 px spawn offset,
so every shot from the same planet has the same origin), sets
`this.startPlanet = planet`, resets `farthest = 0` and `dnf = false`, and copies
`this.maxDist` / `this.returnToStart` from the rule that `startGame` stamps on
every sim. After every
`advance` in `stepOne`/`routeStep`, before the end checks:

	dx = state.x - startX
	dy = state.y - startY
	d  = Math.sqrt(dx * dx + dy * dy)
	if (d > this.farthest) { this.farthest = d; this.farthestX = state.x;
		this.farthestY = state.y; this.farthestStep = step; }

Length is still the odometer (`flightLength`, `routeLength`), so `route` is
unaffected. The score is `farthest`, displayed in px (and in “screens” only in
help text).

`farthest` is the geometric maximum and is never overwritten; it is what the
stat line shows even on a failed run. `finish` adds a separate `dnf` flag for a
return run that lands anywhere except the start planet, and the **score** is
`dnf ? 0 : farthest`. This keeps "how far did it get" and "what did it score"
from being the same field.

## 2. map width

The world is 1600×1000 today; `GravitySim` already accepts `(worldW, worldH)`,
but `OrbitWorld` and the page construct everything with the constants. Make the
width a **world property**, defaulting to 1600:

	OrbitWorld.create(seed, rand, { width, height, planets, periodic })
	OrbitWorld.WORLD_W / WORLD_H     // default 1600 / 1000, unchanged
	world.width = width
	world.height = height
	world.planetCount = planets      // default OrbitWorld.PLANETS, classic 48

Every `WORLD_W` inside `orbit_world.js` placement (`placePlanets`,
`placeExtraPlanets`, `placeOrbits`, `room`) reads `world.width`; `placePlanets`
still places the historical 26 and `placeExtraPlanets` fills up to
`world.planetCount`, so the default call keeps the classic seed bytes. The
max-distance map asks for 78; the 192-array capacity is the `0.7.0` change (or
the same `PLANETS=192` / `MAX_BODIES=192` change made here if this lands
first). `OrbitSim` gets `sim.worldW/worldH` (via
`setWorldSize(w, h)`) and passes them to `OrbitWorld.create`; `Sim.WORLD_W`
stays as the default for the benches.

`GravitySim.setWorldSize(w, h)` updates `worldW`, `worldH`, `padX`, `padY` and
the FFT grid (if periodic); arrays are already `MAX_BODIES` and do not resize.
Call it on `cargoSim`, `helperProbe`, `bot.probe`, `bot.exitProbe`,
`bot.burnShotSim`, every rival `sim` and every fleet `sim` before the mode
starts.

For the max-distance family:

	MAXDIST_SCREENS = 3
	MAXDIST_W = OrbitWorld.WORLD_W * MAXDIST_SCREENS   // 4800
	MAXDIST_H = OrbitWorld.WORLD_H                     // 1000
	MAXDIST_PLANETS = round(OrbitWorld.DEFAULT_PLANETS * MAXDIST_SCREENS) // 78
	MAXDIST_STEPS = 240 * 120                          // 28 800 = 240 s

This is about two to four screens, keeps the 165 px placement gap and the same
density as classic 26/1600, and stays below `MAX_BODIES = 192`. The default
career/lab is still 13/26; only the max-distance rows change the world.

**No wrap in this mode.** The FFT torus is a different topology (`0.7.0`); a
torus has no farthest point (the maximum distance from a point is W/2 in each
axis, and then it decreases again). The mode therefore runs on the long strip
and disables the `periodic FFT` checkbox, with a tooltip that says why. If a
periodic max-distance variant is ever wanted, it is a lap score (unwrapped
displacement), not this rule.

## 3. the two modes

Add two rows to `RULES` and to the mode radio row; no new drawer:

	maxdistEmc: {
		name: 'maxdist-emc', capSteps: MAXDIST_STEPS, horizon: null,
		maxShots: 1, stopOnTour: false, planner: false, solo: false,
		pause: false, maxDist: true, returnToStart: true, allowImpulse: false
	}
	maxdistImp: {
		name: 'maxdist-imp', capSteps: MAXDIST_STEPS, horizon: null,
		maxShots: 1, stopOnTour: false, planner: false, solo: false,
		pause: false, maxDist: true, returnToStart: false, allowImpulse: true
	}

`MAXDIST_STEPS` is a chosen flight cap (240 s at `DT` = 1/120 is 28 800 steps);
it is a race wall, not a range. `maxShots: 1` means one entry per slot, which is
the “land ends the entry” rule; each slot's own `shots` array already enforces
it. `PATH_MAX` (28 900) is just above 28 800, so the stored path still fits; do
not raise the cap past 240 s without raising `PATH_MAX` or accepting the
compressor. The aim preview must use `predictFull` (or raise
`GravitySim.MAX_STEPS`, still 7 350 = 61 s): `predict` would stop a 240 s shot
at 61 s and the preview would lie.

- **`maxdistEmc`** — no impulse engine, no burns. Launch at any rail speed the
  player can charge; fly a ballistic path; the ship must return and land on the
  start planet. Score = `farthest` only if `endBody === startPlanet`; otherwise
  DNF. The EMC-only return is a gravity-slingshot puzzle; the cap and the
  seeded start planet are the level.
- **`maxdistImp`** — one impulse engine and a big preinstalled tank; the first
  landing on any planet ends the entry. Score = `farthest` at the end (landing,
  exit or time). This is the “reserve half the fuel to come back” variant made
  a one-way race: the tank is sized for one long burn, not for a return.

The mode row caption says `max distance · EMC · return` and
`max distance · IMP · land far`, so the difference is visible without a help
drawer read.

### start planet

One planet, the same for every slot: `game.startPlanet`, picked from the
left-edge band (`planetX < margin + 200`) by the seed. Every slot starts
**landed** on it, with `at = startPlanet`; `aimBody` is locked to it until the
first launch and the HUD says `start · P12`. The mode has no pads and no EMC
network (`sim.pads = null`), so the launch gate is the sim's speed/force cap,
not `careerCanFire`; no planet is claimed by launching.

The first landing (other than return) ends the slot's entry. A ship that is
still flying at `capSteps` ends on `END_TIME` and keeps its farthest point in
`maxdistImp`; in `maxdistEmc` it is DNF because it did not return.

### return

`returnToStart` is checked in `finish`:

	if (this.maxDist && this.returnToStart &&
		(reason !== END_IMPACT || body !== this.startPlanet)) {
		this.dnf = true;
	}

`END_EXIT` and `END_TIME` are DNF in the return mode. The stat line still shows
the farthest point and where the ship was, but the score is 0. This is the
whole tension of the variant: a farther point is only worth something if the
ship can turn around.

## 4. the ship

`careerRule()` is the only rule with `career.ship`; the max-distance rows need
the same fit for the IMP variant and a mass for the EMC variant. Add a small
mode ship, not a career:

	game.modeShip = {
		hold: OrbitTech.HOLDS[0], engine: null, tank: OrbitTech.TANKS[0],
		obs: OrbitTech.OBS[0], cargoTons: 0, fuelKg: 0, mass: 0
	}

- `maxdistEmc`: no engine, `fuelKg = 0`; `mass` from `OrbitTech.shipMass`.
- `maxdistImp`: `engine = OrbitTech.ENGINES[0]` (IMP-1), `tank = the largest
  stock tank`, `fuelKg = tank.fuelCap`, `mass` recomputed.

`canImpulse()` becomes:

	if (replay.on || playerIsBot()) return false;
	if (careerRule()) { ... existing career ship/fuel test ... }
	if (maxDistRule()) return activeShip().engine !== null &&
		activeSim().status === STATUS_FLYING && activeSim().burnLimit() > 0;
	return false;

`executeBurn` reads `career.ship` today; it gets `activeShip()` returning the
career ship in career and `game.modeShip` in max-distance. Fuel is per slot in
these modes; each slot gets its own `modeShip` copy (`slotModeShip[slot]`) so a
two-player race does not share a tank. The HUD's fuel line reads the slot ship.

This is the only place the mode touches the ship; no pads, contracts, science
or repair. `0.7.2` wear does not apply to the standalone race (there is no
career condition); a career sport rule can apply it.

## 5. start and scoring

`startGame` knows the rule before it builds the world:

	if (RULES[next].maxDist) {
		tradeSim.setWorldSize(MAXDIST_W, MAXDIST_H);
		cargoSim.setWorldSize(MAXDIST_W, MAXDIST_H);
		bot.setWorldSize(MAXDIST_W, MAXDIST_H);
		helperProbe.setWorldSize(MAXDIST_W, MAXDIST_H);
		initPlanetUniverse(MAXDIST_PLANETS);
	} else {
		resetWorldSize();
		initPlanetUniverse(planetUniverseDefault(next));
	}

`game.startPlanet` is chosen **after** `applyPlanetUniverse` by scanning the
placed planets for the left-edge band, then stored before the first `spawn`;
`startGame` stamps `maxDist` / `returnToStart` on `tradeSim`, `cargoSim`, every
probe and every rival sim; `slotModeShip` is filled per slot; `aimBody =
startPlanet`; `armed = false`; the first drag aims from the start.

Per-slot results are `slotFarthest`, `slotFarthestStep` and `slotDnf`, reset in
`startGame` and copied from `sim.farthest/farthestStep/dnf` when the slot ends.
`slotScore(slot)` for the mode returns the **score**, not the raw geometric
distance: `slotDnf[slot] ? 0 : slotFarthest[slot]` (px). The scoreboard row
uses both:

	scoreValue = score px (0 while flying until the first point)
	meta = flying · 1234 px · max 2345 | landed P7 · 1820 px | DNF · 1820 px

`compareScores` for `maxdist` sorts by `slotScore` (descending), then by
`farthestStep` (earlier is better), then `slot`; `game.length` is not used. The
HUD's `traj length` stat is relabelled `farthest` and prints `1234 px`.
`encodeLink` carries the score in the existing `&len=` field (route already
uses `len` as its score); decode stores it in `game.length`/`game.farthest`.
The `end=visited.steps` field is unchanged; a max-distance link has one shot
and a farthest.

`game_bench`/`dom_smoke` get a `game=1&seed=…&rule=maxdist-emc` boot and a
`game=1&…&rule=maxdist-imp` boot; the link round-trip must preserve `len`.

## 6. camera and field view

`orbit_view` currently fits `FIELD_BOX`/`AREA_BOX` constants. Make them derive
from the sim:

	FIELD_BOX = { x: 0, y: 0, w: sim.worldW, h: sim.worldH }
	AREA_BOX  = { x: -padX, y: -padY, w: worldW + 2 padX, h: worldH + 2 padY }

`resize()` keeps `view.scale = min(availW / box.w, availH / box.h)`, which is
exactly “scale the long map to fit a single screen”: at 4800×1000 in a 16:9
window the whole strip is visible and the height is letterboxed. The user's
answer chooses this over a scrolling camera; the `full area` frame stays
hidden in this mode (there is no margin).

The trade backdrop draws the single field rect and the area edge at the same
scale; `paintBackdrop` already takes `view`, so it only loses the constants.

At 4800 px and 78 planets, `MAX_BODIES = 192` and the classic WebGL shader
(`uBodies[48]`) cannot loop the field. The max-distance rows force the **2D
field renderer** (`fieldRenderer`'s existing CPU path) and the classic planet
body loop is not used; the shader stays at 48 for the 26/48 world. This is the
same rule as `0.7.0`'s periodic view, without the FFT.

Planet labels, visit rings and the start marker are drawn through the existing
projection; at the fitted scale the planet radius is ~3 px, so the mode's help
says to use the labels rather than the discs. A follow/zoom camera is a later
feature, not this plan.

## 7. career sport rules

A career already has `competitions` and `TASK_COMPETE` (a landing task). Add a
third competition shape, `SPORT_MAXDIST`:

	record = {
		variant: 'emc-return' | 'imp-landfar',
		start: planet,
		startsAtStep, deadline,
		entryFee, reward,
		entrants: [career.index, ...]
	}

- The generated sport rule picks a start planet and a variant from the galaxy
  seed, offers it on the board for a window, and accepts entries; the existing
  `TASK_OFFERED`/`TASK_ACCEPTED` flow and `startsAtStep` countdown are reused.
- On the start step, every entrant's ship is placed on `start` and the run uses
  the same `farthest`/`returnToStart` logic; a landing ends the entrant.
- The reward is paid from a pool, priced against `map statistics` (0.6.10) the
  same way `TASK_COMPETE` is; the pool is not new money if the entries are
  paid, it is a purse transfer.
- A career sport run uses the career ship (so `0.7.2` wear and fuel apply); the
  separate max-distance modes use `game.modeShip` (no wear, no pads). This
  split is deliberate: a sport rule is a company event; a mode is a time
  trial.
- `0.6.4` already owns the timed competition event; this plan adds the
  max-distance **shape**, not a second competition system. If the timed event
  is not landed yet, the mode rows ship first and the career shape waits.

## order

1. `world.width/height` + `setWorldSize`; all classic benches byte-identical.
2. `farthest` accumulator and `finish`/DNF; a headless ballistic shot.
3. Two rule rows, start planet, no-pad launch, score rows.
4. Long map (4800), 78 planets, 2D field, fitted camera.
5. `modeShip` + IMP burn + fuel HUD; EMC return test.
6. Career `SPORT_MAXDIST` after `0.6.4`'s timed event; not before.

## validation

- `experiments/maxdist_test.js`:
  - a shot on the 4800 strip has `farthest` within 0.01 px of the maximum
    `hypot(x-startX, y-startY)` over its stored path;
  - landing on a non-start planet in `maxdistEmc` gives `dnf=true`,
    score 0; the stat keeps the geometric maximum;
  - landing on the start planet scores the geometric maximum;
  - `maxdistImp` landing anywhere scores; `END_EXIT`/`END_TIME` score the
    geometric maximum;
  - `MAXDIST_PLANETS = 78`, no pair closer than 165 px, all `x` inside
    `[110, 4690]`;
  - `sim.worldW`/`worldH` and `FIELD_BOX` are 4800/1000 in the mode and
    1600/1000 after a switch back;
  - a `#game=…&rule=maxdist-emc&len=1234` link round-trips.
- `dom_smoke`: both radios, start planet locked, score row says `farthest`,
  camera fits the strip, `full area` hidden; `maxdistEmc` disables periodic FFT.
- `game_bench`/`bot_bench` without the mode: byte-identical.
- `node --check` every touched script; `git diff --check`.

## scope boundary

No KSP burn planner, no “relaunch” variant, no periodic/torus max distance, no
follow camera, no new renderer beyond the existing 2D field path. No change to
`route`/`tour`/`money` worlds or to the career economy. The start planet is one
planet for all entrants; it is not a new HQ or a claim. Career sport rules wait
for the timed-competition event; the two standalone mode rows do not.
