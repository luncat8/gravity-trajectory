# 0.5.9 plan — burn rescue ring when the ballistic fan finds nothing

Standalone spec: a fork can rebuild this from this file alone.

## Goal

When a career company with an impulse engine and a tank has no ballistic plan at
all, price a bounded ring of launch angles by the landing its one-burn flight
can reach. Take the best shot whose landing clears the launch fee, battery wait
and fuel cost and beats sitting still by `CAREER_BURN_PRICE_MARGIN`. This is the
prerequisite for the fuel economy: a fuel detour must be selectable even when
every purely ballistic trace fails. It does not change impulse policy, replay
encoding, the launch book, or human aiming.

## Trigger and gates

- Run only inside `careerNextShot`, after the normal fan, the long-horizon
  fallback fan and the commercial-rail passes, and only when all of them return
  `null`. A finite ballistic plan — including a negative one that the existing
  `careerSit` policy may decline — is still a plan; rescue must not replace it.
- Require `career.at >= 0`, `ship.engine`, `ship.tank`, `ship.tank.fuelCap > 0`,
  `sim.canLaunchFrom(origin)`, and a live speed cap at or above `SPEED_MIN`.
  `ship.fuelKg` may be 0 while parked: `careerBeginFlight` currently fills the
  tank, so the scratch search models a full tank. If 0.5.10 removes automatic
  refuelling, it must update this assumption in both 0.5.8 and 0.5.9.
- Use the rail selected at the end of the commercial pass. If that pass selected
  the commercial rail and rescue succeeds, keep `career.commercialPlanet` set so
  the queued shot fires from the same rail and pays the same fee. Clear it only
  when rescue also fails. A rescue on a drained own EMC must not silently lose
  the commercial fallback.
- Initialize every actor's first-flight `burnNext` to `CAREER_BURN_AT`. The
  previous zero made the first live flight burn at step 0 while 0.5.8 priced the
  same flight at step 24, so the queued and flown landings could diverge.

## Bounded search

- Constants: `CAREER_RESCUE_ANGLES = 16`,
  `CAREER_RESCUE_SPEED_FRACTION = 0.6`,
  `CAREER_RESCUE_SHOTS = (16 + 2) * 2 = 36`, and the existing
  `CAREER_BURN_PRICE_MARGIN = 0.5`.
- Angles: 16 evenly spaced bearings (`22.5°` apart), plus the active contract's
  bearing and its opposite when a contract exists. Snap each bearing into
  `GravityGame.angleUnits` and deduplicate the integer units in a preallocated
  `Int32Array(18)`.
- Speeds: the current pad's `capU` and `round(capU * 0.6)`, both clamped to
  `minU`; skip a duplicate rung. Check `GravityGame.careerCanFire` for each rung,
  so an unaffordable fee or an unfirable rail costs no traces.
- For each `(angleU, speedU)` pair, reuse the dedicated `burnShotSim`: mirror
  the live field, scales, mask, visit log and landed body; set the step limit to
  `CAP_STEPS`; launch; step to `CAREER_BURN_AT`; then call the existing
  `careerBurnPlan(..., rescueOnly = false, fee)`. Search with `ship.fuelKg =
  fuelCap` and restore the real fuel afterwards. Restore the shared probe's
  field, scales and visit log before returning.
- Rescue keeps the existing `careerBurnGain` coast margin. Its scratch flight
  and the real flight then choose the same burn: both start from a full tank at
  step 24, and the pre-launch `fee` produces the same post-fee solvency state
  as the live `fee = 0` call. The extra rescue gate is against doing nothing,
  not a second impulse policy.
- Worst case: 36 launches × (24 integration steps + at most 47 burn traces) —
  about 1,700 prediction traces — once per dead-end plan. No per-candidate
  objects, arrays or closures are allocated; the winning angle list, speed rungs
  and winning snapshot are preallocated on the bot.

## Pricing and plan

For each burn candidate:

```
score = burn.score - fee - energy * wait * CAREER_ENERGY_WAIT_COST
```

`burn.score` already subtracts `fuelKg * CAREER_BURN_FUEL_COST`; `fee` is also
passed into `careerScoreFacts` so the unpaid launch fee gates solvency. Accept
only a finite landing with `score > CAREER_BURN_PRICE_MARGIN` — a sit is worth 0
— and keep the highest score. Fold the fuel cost into `taskPay` so the plan's
money identity `score = taskPay + padValue − fee − energy·wait·cost` holds.

Rebuild `careerBest` from the winner: origin, angle units, speed units, angle,
speed, landing body, score, money terms, fee, energy, wait, exit cost/source,
build flag, `fromBook = false`, steps and burn gain/body. Set `length = 0` and do
not add the rescue to the launch book: it is not a ballistic trajectory. No burn
is pre-applied; the real flight still runs its own mid-flight controller.

Do not call `careerPriceBurn` on a rescued plan. Increment `careerBurnRescues`
and `careerScan.rescue`, and log
`burn rescue · P{origin}→P{body} · {gain} over sit · {n} shots priced`.
`careerBurnPrices` remains the 0.5.8 shortlist-pricing counter.
