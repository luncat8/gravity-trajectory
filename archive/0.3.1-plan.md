# 0.3.1 — game rule `route`: a shot with no length limit

Standalone spec. A fork can build this from this file alone: it defines the
`route` game rule, the resumable tracer that makes a long preview free, and the
measurements that shaped both.

## 1. why a second rule

The `tour` rule caps a flight at 120 s (`CAP_STEPS = 14 400`) because that is
what the score needs: systems, fewest shots, least time. `route` inverts the
last term — a long sweeping trajectory is the thing being rewarded — so the cap
has to go, and the preview has to survive a horizon the frame budget cannot pay
for in one call.

Measured in the shipped world (seed 31, 26 static bodies, `t+07:00`, 6 864 grid
shots at every planet × 24 angles × speeds 30…320):

| quantile | flight |
| --- | --- |
| median | 5.7 s |
| p95 | 37.1 s |
| longest | 158.3 s |
| over the 120 s tour cap | 4 shots (0.06 %) |
| reaching the 1 800 s wall | **0** |

So the wall is a net, not a routine end: gravity wells here are shallow, the
world is 1 600 × 1 000, and every unedited shot either lands or leaves the
field inside ~160 s. What the mode really buys is the 120 s cap disappearing
for those long slingshots plus a score that pays for distance. The tracer is
still required, for two other reasons: a 160 s trace costs ~4.5 ms static and
~9 ms with moving ports (a dropped frame on every aim edit), and the bot rule
in `0.3.3` evaluates many long candidates per decision.

## 2. rules

- Same physics, same world, same fixed `DT = 1/120`, same launch bases, same
  gravity editing as `tour`.
- A flight ends on **impact**, **leaving the field**, **abort**, or the
  **1 800 s wall** (`ROUTE_STEPS = 216 000`). The wall and the horizon are the
  same number: the tracer's `END_TIME` *is* the wall, so no new end reason is
  needed and none is added.
- Score, in order: **systems visited**, then **route length** (sum of the flown
  paths in px, larger is better), then **fewer shots**, then **less flight
  time**.
- The aim's trajectory is traced to its end before the shot is recorded, so the
  player sees where it lands however long it takes.
- A run is still a pure function of `(seed, rate, rule, shots)`; the purse/bot
  work in `0.3.2`/`0.3.3` builds on the same shot list.

## 3. the resumable tracer

`GravitySim` owns one trace job; the old one-shot `traceProbe` is gone and every
caller goes through the job:

```
routeBegin(origin, angle, speed, horizonSec)   // spawn + snapshot, stride 1
routeStep(budgetMs) -> bool                    // true when the job is finished
routeDrain(budgetMs) -> bool                   // loop until finished or the budget runs out
routeProgress() -> 0…1                         // steps / maxSteps, for "computing 43 %"
predict(origin, angle, speed, budgetMs)        // = begin(this.horizon) + drain(budget)
predictFull(origin, angle, speed, horizonSec)  // = begin + drain(1e9): launch, benches
predictFlight(budgetMs)                        // = begin-at-live-cargo + drain, field restored
```

- `routeStep` runs at most `budgetMs` of tracing, checks the clock every 64
  steps, and commits into the shared `pred*` readouts (count, time, length,
  visits, new visits, reason, body) at the end of **every** slice, so a paused
  job already shows its visits and length and the canvas keeps a real path.
- **Point buffer**: full resolution at stride 1 until `PATH_MAX = 28 900`
  points, then the path is compacted 2:1 in place and the stride doubles —
  the same policy as the trail, no state to carry across slices. Real shots
  keep every step (a 158 s shot is 18 997 points); a pathological 1 800 s wall
  trace ends at 27 001 points and stride 8.
- The end point is always stored, so a sampled path still lands on the truth.
- The job is a snapshot: a sliced preview is not restarted by every world tick.
  In moving-port mode it restarts when the field has advanced more than
  `ROUTE_FIELD_DELTA = 4` s of field time, and always on an aim edit.
- Launching (`fire`) traces synchronously with `predictFull`, so a link or a
  bench never records a half-computed shot; the preview only has to look right.

## 4. rules table and replay link

`gravity_game.js` holds the per-rule constants in one table — the GUI reads the
cap and the horizon from it, nothing is duplicated:

```js
RULES = {
	tour:  { name: 'tour',  capSteps: 14 400,  horizon: null },  // null = the horizon slider
	route: { name: 'route', capSteps: 216 000, horizon: 1 800 }
}
```

- The link gains `rule=route` when the rule is route — tour links stay
  byte-identical, so `FORMAT` stays `1`:
  `#game=1&seed=31&rate=3&rule=route&shots=…&end=13.2374`.
- `decodeLink` maps a missing `rule` to `tour` and rejects any other value.
- An abort is rejected at or above **the rule's** cap (`decodeShot(text,
  capSteps)`), so a tour link cannot smuggle a 121 s abort in and a route link
  can carry one: `p0.0.3aio.ba0` (14 616 steps = 121.8 s) decodes under
  `route` and fails under `tour`.

## 5. UI

- A `rule` radio (`tour` / `route`) in the game box with a one-line tag:
  `tour · 120 s cap` / `route · 30 min wall`. Changing it restarts the same seed
  — a rule is part of the run.
- While a sliced job runs, `time to end` reads `39.5 s · computing 43 %`; the
  `traj length`, `pred visits` and `calc` readouts update from the committed
  slices.
- The score line gains the run's route length: `13 / 26 · 3 093 px · 2 shots ·
  19.78 s`.
- Nothing else changes: the horizon slider still drives `tour` and the lab, and
  the in-flight continuation keeps its 240 s drawing horizon.

## 6. acceptance and measured results

`experiments/route_bench.js` (new):

| check | result |
| --- | --- |
| one call vs 1 ms slices, point for point (200 static shots, 60 moving-port shots, plus a wall shot that compacts 3×) | identical: reason, body, steps, time, length, visits, stride, every stored point |
| wall trace (no gravity, huge world) | 216 000 steps, 27 001 points, stride 8, 28.5 ms of work in 8 slices |
| longest real shot | 158.3 s, 18 997 points, stride 1 |
| slice cost, 4 ms budget, 1 800 s horizon | static 0.4 ms in 1 slice; moving ports ×6 1.0 ms in 1.3 slices; worst slice 4.02 ms |
| allocation | probe, path, field and visit buffers keep their identity across a trace |

`game_bench`: a route run (seed 31, rate 3) reaches `13 / 26 · 3 093 px · 2 shots
· 19.78 s`; the copied 78-char link carries `rule=route` and replays identical
at ×1, at 4–45 ms jitter with 120 ms stalls, at ×16 and by skip, `verified ✓`.
`dom_smoke`: rule radio restarts the run, a route preview is the whole 1 800 s
horizon (`routeMaxSteps = 216 002`) and repeatable, the flight cap is
`ROUTE_STEPS`, the score shows px, the link replays and verifies.

## 7. risks

- **Long flights age the colonies.** The trade clock advances with the flight's
  field time; 1 800 s at rate 3 is 90 sim minutes. Both rules are seeded, so
  comparisons inside a rule stay fair, but a route run is not comparable to a
  tour run's colonies.
- **Repel-heavy gravity editing** is the case the wall exists for; `END_TIME`
  shows it as `time cap`, and the tracer's compaction keeps the buffer flat.
- **Drawing**: 27 001 points at the existing stride-4 threshold is 6 750
  segments — the same as today's worst case; real shots draw every step.
- **A moving-port snapshot** is up to 4 s of field time stale; the aim readout
  is the truth at launch, and `fire` re-traces synchronously.
