## Planning resolution fixes (this session)

The WS4 planning state broke three existing page tests; all were caused by the
planning state being entered but never resolved, or resolved in a way that
left the page inconsistent. Fixes, none of which weaken any assertion:

- **`stepCareerPlanning` auto-advance + resolve.** A tier that completes
  without being accepted now auto-advances to the next tier (`advanceTier()`),
  and when the walk is exhausted the run resolves: `bestPlan()` →
  `applySeatPlan` if a plan exists, else `startCareerWithPlan(null, …)` with
  the pickHq fallback. This is what lets seed 7's roster (no accepted tier)
  still start. Both `applySeatPlan` call sites capture the search before
  `cancelCareerPlanning()` nulls it. `playFairSearchAsIs` falls back to the
  pickHq start when there is no plan.
- **`finishCareerStart` records the opening.** The planning path starts the
  career asynchronously (after `startGame`'s tail), so
  `careerRecordingReset()` is now called at the end of `finishCareerStart`,
  after `bot.startCareers`, so the recording's roster snapshot is complete.
  `career_actions_test` (seed 7 copy/replay) required this.
- **`gameLocked` holds during planning.** `gui_predict.js` `gameLocked()`
  returns true while `GravityScene.careerPlanning()`, and the
  `slotCareer(slot).evacuating` read is guarded, because a planning run has no
  career record yet (`career_actions_test` crashed here).
- **`refreshLaunchList` holds during planning.** `gui_book.js` returns before
  reading `activeCareer()` while planning, and guards a null career.
- **Harness planning drain.** `experiments/dom_stub.js` now resolves the
  planning state with a new planning-only driver — `GravityScene.drainCareerPlanning()`
  (`gui_game.js`, loops `stepCareerPlanning` without stepping the game clock) —
  at page load, after every `click`, and at the end of `runFrames`. This keeps
  a loaded/clicked career page in the started state the way it was before the
  planning state existed, without advancing the clock ahead of a fresh replay
  (which broke `career_actions_test`'s exact-step replay). `player_growth_test`
  (restart with a large roster) needed the post-click drain.

### WS4 decision lifecycle (documented UX, then implemented)

UX record (written before touching the drain helper, per the review):
- A tier that accepts or completes freezes a decision
  (`careerPlanDecision`: `accepted` | `tier-end`, snapshot plan, canAdvance).
  The walk stops; the clock stays held; only completed tiers can become a
  plan; wall-clock decides when the card appears, never which sets were seen.
- H's fair-search card then offers: **play as planned** (the snapshot tier),
  **search more** (`advanceTier()`, walk resumes, live report continues),
  **load a fair save** (inline `<select>` of saved career records re-scored
  through `openingGroupStats` at the 0.55 band, memoised; picking one loads
  via `startMapRecord`), and **start fair** when a tier accepted.
- `drainCareerPlanning()` keeps its signature and guard and now plays a
  patient simulated player: wait-more while a tier can still advance, then
  play-as-is; an accepted tier starts fair at once; the no-plan fallback is
  unchanged. That reproduces the old walk-every-tier outcome for every
  existing harness test. (The harness's `click()` path also drains, so tests
  that inspect a pending decision open the card with `commsOpen()` directly.)
- `createSeatSearch.canAdvanceTier()` is the read-only probe behind
  search-more's enabled state; `commsBuildSnapshot` now passes roster and
  search fields FLAT (passing them nested left `rosterOk`/`searchActive` at

## 2026-11-24 session 3 — the matrix contract-vs-ladder decision

### Decision: the ladder is the contract's measure

The `C=20 S=6 seed 5` failure was the last open item. Probed the cell
directly: `prepareCareerStarts` plans `[17,13,10,8,9,18]` (ratio 0.54),
while the completed T1 ladder plans `[8,15,14,12,7,13]` — minPay 1.303 /
maxPay 1.905, ratio **0.684**, matching the alt-HQ oracle's 0.68, in ~13 s
of background work (plan target ≤ 30 s). The ladder is what the page
reaches with search-more, so the contract now measures it.

### Harness change (`experiments/career_start_fairness.js`)

- New `ladderSample(world, count, seats)`: runs `createSeatSearch`, steps
  every tier to completion (`step(Infinity)` + `advanceTier()` while
  `canAdvanceTier()`), and re-verifies the ladder's best plan through the
  same independent `checkOpening` (pay-window matcher, exact group stats,
  game witness) the tier-0 plan already gets. Wall time is measured around
  the tiers.
- `runCell` for `count >= 20`: a tier-0 plan that misses the band is
  re-measured through the ladder before the cell is called broken; a fair
  ladder rescues the cell (`ladder N/12 ms` column, `ladder-rescued` in
  the summary). Tier-0 plan time keeps its own `MEAN_MS` assert — the
  ladder is background work and never enters that budget. No band, no
  saved-map pin and no assertion was weakened.
