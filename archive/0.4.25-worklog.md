# 0.4.25 worklog — launch list tab, rail facts, book-seeded helpers

Plan: `0.4.25-plan-launch-tab.md`. User brief: review the launch list and
improve it if a good way shows up; the auto helpers should use a saved result
when it is better than what they searched; the list needs its own tab; rename
`operations` to `upgrades` so each tab has one job.

## Review of the delivered launch list (0.4.23 / 0.4.24)

- **A stale book was reported as "empty".** `launchListHtml` asked
  `bookReady()` and printed `empty · aim or scan from P#`. After a gravity edit
  the book still held N shots; the rows disappeared without a word and the next
  save dropped them silently. Nothing offered to clear them.
- **The reason for a disabled `use` lived only in `title`.** Chrome and Safari
  do not fire mouse events on disabled buttons, so on most machines a blocked
  row had no explanation at all. The refusal in `useBookEntry` used different
  words than the tooltip, and neither matched the bot log.
- **`useBookEntry` never checked the tag**, so a programmatic click (or a DOM
  state left over from before a field change) could arm a path that no longer
  holds.
- **The refresh key was too coarse**: `book.version + career.at + fieldStatic +
  clock/240`. A purchase or a pad drain changes the fee, the cap and the money
  in every row without changing that key, so the list kept a stale verdict.
- **Two hand-kept copies of the money terms** (`rankLaunchList` and
  `traceMoney`), and a third in the bot. They agreed today by inspection only.
- **`helperScore` ranked a shot by money but never checked the purse against
  the fee**, so a scan could arm a shot the launch button then refused.
- The list only ever showed the planet under the ship, which is why it did not
  deserve a tab.

## Implementation

### Shared rail facts (`gravity_game.js`, `gravity_bot.js`)

- `railOwnerText(career, planet)`, `railText(career, sim, planet)` and
  `railBlock(career, sim, planet, speed)` moved next to the career model.
  `railText` is the exact line the bot log printed as `careerRailText`; the
  page list prints it too.
- `railBlock` returns `''` for a firable shot, else `ship in space`,
  `shot leaves from P#`, `no rail under the ship`, `cap 33 < 61 px/s` or
  `fee 3.00 > purse 0.50`. `careerCanFire` is now `railBlock(...) === ''`, so
  the launch button, the list row and the bot cannot disagree.
- The bot: `careerRailText`/`ownerText` deleted, `actorStatus` and the queue
  line call the shared helpers, and `careerNoPlanWhy` composes its cap and fee
  reasons from `railBlock` (keeping the charge behind a cap).

### Page (`index.html`, `gravity_gui.js`, `style.css`)

- Three tabs, one job each: `upgrades` (planet picker, pad, task board, shop,
  evacuate), `shots` (the launch list) and `science`. `#careerOperations` is
  `#careerUpgrades`, the tab table is a flat array, and the default is
  `upgrades`. Keyboard/aria state follows the same table.
- The shots tab prints the live rail line for the planet under the ship (or the
  evac line in space), a `N saved · M fireable here` count, then the whole book:
  fireable rows first, best live money first, each row `kind · landing · time ·
  net` plus a `use` button.
- A blocked row is dim, keeps `use` disabled and prints its reason on its own
  line (`.careerWhy`) — `cap …`, `fee …`, `shot leaves from P#`, `no rail under
  the ship`, `ship in space`, `moving field`, `a shot is already queued`, `the
  clock is settling a wait`, `bot controls the ship`. `useBookEntry` refuses
  with the identical string (after the tag check), so the row and the click can
  never disagree.
- A moving field now **pauses** the list (rows listed, all blocked) instead of
  hiding it; nothing is dropped, because the tag comes back with the static
  field.
- A static field whose tag no longer matches says `stale · N saved in another
  field` and offers `clear` (`data-act="bookDrop"`), which drops the book now
  instead of on the next save.
- `refreshLaunchList` keys on book version, tag, planet, flight state, queued
  shot, wait, pad charge, purse and the clock, so every number a row prints is
  also a reason to re-render. `launchListHtml` now escapes text (`escapeHtml`)
  because the block strings contain `<`.
- Money terms: one `moneyFacts()` table feeds `traceMoney(probe)` (fresh trace)
  and `storedMoney(entry)` (visit log at the live market); `moneyFlyable()`
  holds the two live gates (fee covered, landing affordable to leave) and is
  used by the scan, the seed and the row ranking.

### Helpers (`gravity_gui.js`)

- `helperBookSeed(career, origin, requireEmc)` prices the book with
  `estimateProfitLog` (no trace), skips entries above the live cap or behind a
  rail gate, and returns the best saved shot as a candidate-shaped slot.
- `helperRun(..., seed)` puts the seed into `helperState.best`/`bestScore`
  before the first candidate, so the scan has to beat it. `fromBook` follows
  the winner: the notice reads `launch list · P7 · +1.24` when the saved shot
  wins and `best money shot · P7 · +1.10` when a fresh aim does.
- No "good enough" shortcut: the seed costs no trace, so the scan still runs
  and quality never drops. The two money buttons now also require a static
  field and an open career, matching their own disabled state.

## Decisions / open points

- The helper always scans; only the seed is free. A threshold that skips the
  scan would have to be tuned per goal and could return a worse shot than a
  200 ms scan finds.
- The list now shows every planet's shots, but only the current rail can be
  armed; off-planet rows are dim with `shot leaves from P#`. Travel is a
  planning problem (see next step), not a click.
- A moving field pauses rather than clears the book: the tag returns when the
  field is static again, so clearing would throw away valid finds.
- `moneyFacts` returns one scratch object; every caller reads it before the
  next pricing call (documented at the declaration).

## Next step suggestion

Chain saved shots into multi-hop plans: the book already knows A→B and B→C
with their live money, so the shots tab can show a two-leg plan with the total
(`P4 → P6 → P9 · +3.10 · 26 s`), arm the first leg and keep the second as the
next step — the same way the bot prices a known route. A tab badge (saved shot
count) and arrow-key movement between the three tabs are cheap follow-ups.
