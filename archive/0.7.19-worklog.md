## 1. why the window was lost

`switch_project()` was a file dialog plus `subprocess.Popen([gallery.py,
--project, path])` plus `self._on_close()`. On Windows the second process opens
its own window, and the window manager puts it where it likes: the size, the
position and the focus of the window the user had are gone, and the old one
disappears under it. That is the whole complaint - and none of it was needed,
because the only thing a project changes is `launch.py`'s module state.

**`launch.use_project(path)`** does that switch: `core.load_project`, the four
required keys (`name`, `prompts`, `workflows`, `output` - a ComfyUI graph has
node ids for keys, so it fails there rather than halfway), and only then the
`PROJECT_PATH`/`CONFIG`/`BASE`/`OUTPUT_DIR`/`STATE_PATH` globals. Everything
below them in `launch.py` reads those globals when it is called, so the switch
reaches `find_prompt_mds`, `find_workflows`, `parse_prompts`, `patch_workflow`,
`queue_job` and the state path at once.

`gallery.py` had copied `OUTPUT_DIR` into a module constant and used it in
`scan_output`, `index_scan`, `delete_image`, `undo_delete`, `open_output`,
`_worker_download` and a card's Copy path. Those are `self.out_dir` /
`self.trash_dir` now, set at boot and on every switch, so an open gallery cannot
read or write the other project's renders.

Two trap doors found while moving it:

| trap | why it bites | fix |
|---|---|---|
| `launch.load_state(path=STATE_PATH)` / `save_state(state, path=STATE_PATH)` | a default argument is evaluated **once, at import**: after a switch the gallery still read and wrote the first project's `state.toml` | the default is `None`, resolved inside the call |
| `self.save_state_now()` was called after `use_project()` | it would write the old checkboxes into the *new* project's state file | the state is saved first, then the globals move |

`switch_project` then does what the second process used to do by starting fresh:
closes the viewer, drops pending jobs and the undo stack (they belong to the
other project), reloads `state.toml`, re-applies `DEFAULTS`, puts the variations
spinbox and the ComfyUI chips back to the new project's values, clears the
filter, reloads the prompt/workflow/job tables, rebuilds the sidebar lists,
rescans the new output dir and rebuilds the cards - and scrolls the new list to
its top. The title and the toolbar's project label follow.

The worker runs on while that happens, so two of its events needed a guard:
a `rescan` now carries the project it scanned and is dropped if it is stale, and
`_worker_download` captures `self.out_dir` when it starts, so a download queued
before the switch still lands in the directory that job was rendered for.

## 2. the project list

The sidebar's first block is **Project**:

- **discovery** is a property of the file, not of a name: a JSON next to
  `launch.py` with `name`, `prompts`, `workflows` and `output` at the top level
  (`launch.is_project_file`). `gravity.json` and `arc-steam.json` qualify; the
  three bundled workflow graphs do not. Cheap veto on `"prompts"` before the
  parse keeps boot from reading a graph.
- **the list is radios, not checkboxes.** The workflow and prompt-file lists are
  checkboxes because any number can be on; exactly one project is open, so the
  same-looking list uses the control that says so. The styling, the tooltip with
  the full path and the placement match the other two blocks.
- **+ add project…** opens the file dialog, validates the file with
  `is_project_file`, appends it to `photos/generator/projects.json` (git-ignored)
  and switches to it. The next start reads that file back, so a project kept
  outside the generator checkout stays in the list.
- the open project is always in the list, even when it was started with
  `--project` from somewhere discovery does not scan.

`_build_side_lists()` owns all three blocks and destroys/rebuilds them as one
block, because all three change with the project; the sidebar note below them is
project-independent and stays.
