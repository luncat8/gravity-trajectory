# 0.8.0 follow-up — auto-helper proximity-index perf

Branch: `arena/00f4f456-gravity-trajectory`. Continuation of the periodic-FFT
feature: the user confirmed the FFT map looks good and the auto-helpers work
(across planet counts), then asked to speed up the auto-helper scans.

## profile

`experiments/planet_index_test.js` (and an ad-hoc per-call probe) measured the
per-step cost of a periodic prediction on a 3200×2000 torus:

- `advance` (gravity) — ~0.0002 ms/call, **O(1)** in planet count (the FFT
  snapshot, as intended).
- `stepInsideAt` — 0.0004 → 0.0039 ms as K: 16 → 192 (linear in K).
- `impact` — 0.0005 → 0.0042 ms as K: 16 → 192 (linear in K).
- total physics per candidate ~flat across K (~1–1.6 ms): denser maps → shorter
  flights, so the N-scaling of visit-marking is cancelled by fewer steps.

Conclusion: gravity was already decoupled from N by the FFT; the only remaining
N-scaling in the helper's per-step loop was the brute-force scan over every
planet in `impact`, `stepInsideAt` and `markSystemsAt`. That is what the user
noticed as "slow … despite planet number" — the slowness is present at every
planet count (a fixed per-candidate cost) because visit-marking still costs
O(K) per step.

## fix

Added a **uniform bucket spatial index** over planet positions in
`gravity_sim.js`:

- `buildPlanetIndex()` (called from `setPlanets`, `setPeriodic`, `setWorldSize`):
  square cell grid; each planet lands in one cell; only built when
  `periodic && planetCapacity > 48` (classic K≤48 keeps the validated brute
  loop, zero risk to the classic physics fingerprints).
- `collectNearbyPlanets(x, y)`: fills a reused `Int32Array` with the planet
  indices in the ±`planetNearR` cell neighbourhood (torus wrap via mod), no
  allocation.
- `impact` / `stepInsideAt` / `markSystemsAt` fall through to the *same*
  brute-force code when `!periodic || !planetIndexValid`, and use the index in
  periodic mode.

Correctness is preserved exactly: a planet can only be entered/landed on when the
query point is within its influence radius (max of system major axis and
`planetR + CARGO_R`), which is ≤ `maxInf`; with cell side `cs ≥ maxInf` and a
±(`ceil(maxInf/cs)+1`) cell scan, every planet whose influence disc contains
the point is inside the scanned cells, so the result set equals the brute-force
one. `impact` returns the smallest satisfying index, matching the ascending
brute loop. Far planets are never relevant, so skipping them changes nothing.

## results

`experiments/planet_index_test.js` (single sim per K, index toggled on/off on
the same layout, 8000 probe points + 60 full predictions):

| K | index | impactDiff | insideDiff | markDiff | steps/body/len match | speedup |
|---|---|---|---|---|---|---|
| 16 | off | — | — | — | — | brute only (no regression) |
| 26 | off | — | — | — | — | brute only |
| 48 | off | — | — | — | — | brute only |
| 64 | on | 0 | 0 | 0 | yes | 1.03× |
| 104 | on | 0 | 0 | 0 | yes | 1.75× |
| 192 | on | 0 | 0 | 0 | yes | 2.06× |

Byte-identical to the brute force at every active count; per-candidate
prediction fully decoupled from planet count (2× faster at 192, and it cannot
get worse as K grows). No low-K regression.

## next

The auto-helper scan is now O(1) in planet count end-to-end (gravity via FFT,
proximity via the bucket index). If the *perceived* wall-clock slowness remains,
the remaining fixed cost is the per-candidate scoring (`traceMoney` / leg
pricing) and the 34-aim frame budget (`HELPER_BUDGET_MS = 3`) — a separate
orchestration optimisation, not physics. The next planned feature after 0.8.0 is
still `0.8.1` (max-distance modes).
