# 0.3.1 worklog — game rule `route` and the resumable tracer

Implements `0.3.1-plan.md`. Started from a review of `0.3.0` (playback speed,
planet photo deck, art prompt pack).

## review of 0.3.0

- The photo deck's candidate chain (variant → plain → jpg → png, CSS postcard
  as the never-failing last step, the loaded URL remembered) has no dead ends
  and no unused constants (`VARIANTS`, `EXTS`, `HIDE_MS`, `COMPACT_W/H`,
  `pending`, `loadedSrc` are all live).
- Playback (`stepGame`, `PLAY_GUARD = 128`, `PLAY_MAX = 32`, the 0.25 s `acc`
  clamp in `GravitySim.step`) is consistent: the multiplier only scales the
  slice fed to the fixed `DT`, which `game_bench` keeps proving at ×16 and by
  skip.
- One weakness worth naming rather than fixing in place: the aim preview gave
  up silently when `BUDGET_MS` ran out — `END_TRUNCATED` drew a shorter path
  with no sign that the picture was incomplete. Route mode needed a job that
  survives the frame, so that is where it was fixed (`computing N %`); `tour`
  keeps the old behaviour, where the `budget cap` label is correct and rare.

## step 1 — the tracer became a job

- `traceProbe` replaced by `routeBegin` / `routeBeginAt(…)` / `routeStep(ms)` /
  `routeDrain(ms)` / `routeProgress()`. `predict`, `predictFull` (new,
  budget-free) and `predictFlight` are now thin drains over the same job, so
  prediction, live flight and benches still share one integrator.
- Each slice commits into `pred*`, so a paused job already shows visits, length
  and time; the GUI keeps drawing the partial path instead of blinking.
- Point policy: stride 1 until `PATH_MAX`, then compact 2:1 in place and double
  the stride — the trail's proven pattern, no cross-slice bookkeeping.
- First attempt sized the stride up front from `maxSteps / PATH_MAX`
  (`routeStrideFor`); the bench showed what that costs: a wall-sized horizon
  would have sampled *every* route shot at stride 8, i.e. 58 points for a 4 s
  hop. Dropped it — real shots keep every step (158 s = 18 997 points) and only
  a pathological trace samples.
- `END_WALL` was added, then removed: with `maxSteps = ceil(horizon / DT) + 2`
  the horizon check always fires first, so the "route wall" *is* `END_TIME`.
  The bench proved it (the wall trace ended with `horizon`), and a second end
  reason that can never be produced is a leftover, not a feature.

## step 2 — what the world actually does

`route_bench` section 2 measured every planet × 24 angles × speed 30…320
(6 864 shots, 1 800 s horizon, static field): flight median 5.7 s, p95 37.1 s,
longest 158.3 s, 4 shots over the old 120 s cap, **0** reaching the wall. Orbital
shots (tangential launch at `sqrt(MU/r)`) do not survive either — the 26-body
field destabilises them inside ~72 s. So `route` is about losing the cap and
scoring distance, and the 1 800 s wall is a net for edited (repelling) gravity.
The plan was rewritten around that finding instead of the original "a 1 800 s
trace is a fifth of a second, so maybe a long shot happens" premise.

## step 3 — rules table and link

- `gravity_game.js`: `RULES = { tour, route }` with `capSteps` and `horizon`,
  `ROUTE_SECONDS = 1 800`, `ROUTE_STEPS = 216 000`.
- `encodeLink` writes `&rule=route` only for route runs, so tour links stay
  byte-identical and `FORMAT` stays `1`; `decodeLink` defaults a missing rule to
  `tour` and rejects unknown names.
- `decodeShot(text, capSteps)` — an abort is validated against the *rule's* cap,
  which is also the fix for a link the old codec test used as a reject case
  (`…ba0` = 14 616 steps = 121.8 s): valid under `route`, still rejected under
  `tour`, and past 216 000 steps rejected under both.

## step 4 — GUI

- `rule` radio in the game box + `ruleTag` (`tour · 120 s cap` /
  `route · 30 min wall`); switching restarts the same seed, because a rule is
  part of the run.
- `frame()` starts the job on an aim edit and advances it 4 ms per frame;
  `aimTraceStale` stops a moving-port world from restarting it every tick (it
  restarts once the field has moved 4 s of field time, or on an aim edit).
- `fire()` traces synchronously with `predictFull` for the rule's horizon, so
  the recorded shot is never half-computed; the preview only has to look right.
- `time to end` shows `39.5 s · computing 43 %` while a job runs; the score line
  gains the run's route length (`13 / 26 · 3 093 px · 2 shots · 19.78 s`);
  `recordShot` takes the cap from `ruleSpec().capSteps`.

## validation

- `experiments/route_bench.js` (new): sliced == one-shot point for point over
  200 static + 60 moving-port shots and a wall shot that compacts 3× (stride 8,
  27 001 points); wall trace costs 28.4 ms of work in 8 slices, worst slice
  4.01 ms; real 158 s shot keeps stride 1; 4 ms slices stay ≤ 4.02 ms; no buffer
  or probe identity changes during a trace. `ROUTE BENCH OK`.
- `game_bench`: route run `13 / 26 · 3 093 px · 2 shots` with a 78-char
  `rule=route` link replaying identical at ×1, 4–45 ms jitter, ×16 and skip,
  `verified ✓`; codec round trips now include route links and a route-length
  abort. `GAME BENCH OK`.
- `dom_smoke`: rule switch restarts the run, `routeMaxSteps = 216 002` on the
  preview, the flight cap is `ROUTE_STEPS`, the score shows px, the link replays
  and verifies. `SMOKE OK`.
- `gravity_bench` and `colony_bench` unchanged and green: parity still 0.000068 px
  (the tracer refactor is exact), worst prediction 3.27 ms of the 10 ms budget.
  Log: `../experiments/logs/0.3.1-bench.txt`.
