## 2. What decides a boundary

The file boundaries are the result of these rules, not of a line budget.

1. **Vertical areas, never technical layers.** No `game_utils.js`, `game_state.js`,
   `game_constants.js`, `bot_helpers.js`, and no empty re-export hub. A part owns its laws, its
   tuning constants, its scratch buffers, its refusal predicates and its state transitions.
2. **A constant or scratch buffer read by exactly one other part moves into that part.** The
   monoliths declare most tuning constants in one top block; a contiguous cut would leave them
   in the core and force a second file for every tuning edit. Measured on a contiguous cut of
   this partition: 59 of the bot core's 92 shared names and ~50 game names (`LEG_SCAN_*`,
   `FRAGILE_*`/`DEEP_*`, `START_*`, `SALT_*`, `OPENING_LAW_*`, `HARVEST_*`, …) had exactly one
   reader elsewhere. Functions are different: a function stays with its subject even when one
   other part calls it (`careerStartTraceText` stays in `bot_trace.js`).
3. **Cohesion beats the target size.** Target 150–750 lines (~2–8k tokens); allow up to ~950
   rather than slicing one algorithm, its scratch arrays and its inner loops across files.
   Keep every per-frame or per-trace inner loop in one file.
4. **Contiguous where the area was contiguous.** A file takes at most three monolith blocks plus
   a short named list of single declarations that belong to it (a helper declared far from its
   users). Every such name is written in the anchor map (§8), so the move stays reviewable; the
   mechanical audit (§8) replaces "it looked contiguous" as the proof.
5. **Mutable state never crosses a file.** A top-level `let` stays in the part that writes it;
   other parts call its accessor (§3.4).
6. **No definition-time read of a later part.** Load order is a DAG; a later part may be reached
   only inside a function body (§3.3).
7. **Self-describing head.** Every part starts with a 3–5-line prose header (what it owns, and
   `not here: <adjacent concern> → <file>` for the nearest wrong-file risk), then its one import
   line. The import line and the publish lines are code, checked by `parts_test.js`; no
   hand-maintained `exports:` comment that can go stale.
8. **The core's `PARTS` array is the table of contents** — load order plus one comment per file.
   `sed -n '/const PARTS/,/];/p' gravity_game.js` answers "which file" in one read.

## 3. Mechanism: private parts attached to the public object and a shared `inner` bag

### 3.1 Why not the alternatives

- **Flat global scripts (the `0.5` GUI mechanism).** The ~870 game and ~120 bot top-level names
  would share the page's global lexical scope with the GUI's ~840 (collisions certain), and Node
  consumers need one CommonJS module per `require`.
- **Parts that publish every shared name on the public object** (`const { … } = GravityGame;`
  imports, `GravityGame.x(…)` back references, each part `require`s the core through a cycle).
  It works and was prototyped on this exact partition, but measured: `GravityGame` grows from
  328 to 440 keys and `GravityBot` statics from 18 to 95 — scratch buffers, caches and tuning
  constants become de facto API the GUI can start calling. Back references through the public
  object also reach test monkeypatches (`fair_start_gui_test` stubs
  `GravityGame.startComposition`/`createSeatSearch`, `career_replay_capture` stubs `buildGear`)
  that internal callers never saw in the monolith, and the two renamed public keys
  (`harvestMode: harvestModeOf`, `specialPlanets: specialPlanetsOn`) make a destructured
  `specialPlanets` bind a function, so `if (specialPlanets)` turns always-true.
- **`G.name` at every cross-part reference.** Rewrites thousands of call sites, the diff stops
  being a move, and hot planning loops pay property loads.
- **One scope rebuilt by concatenation.** Impossible across browser script tags without a build.

### 3.2 Core

Each entry file stays a real module (never an empty hub): it owns the shared vocabulary, the
`PARTS` list, and assembly. Shape, `gravity_game.js`:

```js
(function (root) {
	'use strict';

	/* load order; index.html lists the same files right after this one */
	const PARTS = [
		'game_ship.js',        // ship wear, repair, fuel, evacuation fare, balance knobs
		/* … one line per part, §4 … */
	];

	const node = typeof module !== 'undefined' && module.exports;
	const GravitySim = node ? require('./gravity_sim.js') : root.GravitySim;
	/* … OrbitWorld, OrbitEcon, OrbitTech, OrbitScience, PlanetGravity … */

	/* … core declarations, verbatim … */

	const GravityGame = { /* the core-owned public keys, in their original order */ };
	const inner = { GravitySim, OrbitWorld, /* …externals…, */ CAREER, price, canPay /* …every core name a part reads */ };

	let attached = 0;
	function part(file, attach) {
		if (file !== PARTS[attached]) throw new Error('gravity_game.js: expected ' + PARTS[attached] + ', got ' + file);
		attach(GravityGame, inner);
		if (++attached === PARTS.length && !node) delete GravityGame.part;
	}

	if (node) {
		for (const file of PARTS) part(file, require('./' + file));
		module.exports = GravityGame;
	} else {
		Object.defineProperty(GravityGame, 'part', { value: part, configurable: true });
		root.GravityGame = GravityGame;
	}
})(typeof globalThis !== 'undefined' ? globalThis : this);
```

- **No CommonJS cycle:** the core requires its parts; a part never requires anything.
- **The order is checked at runtime in both loaders:** a part loaded out of `PARTS` order throws
  at load, in the page and in Node.
- **Assembly is core-owned:** after the last part the browser entry point `part` is deleted, so
  no own property is left behind; `comms_copy.js` freezes `CommsCopy` at the same point (§6).
  Nothing runs between the core's tag and its last part's tag.
- `gravity_bot.js` does the same with `function GravityBot` (constructor, field inventory)
  as the public object; `comms_copy.js` with `const CommsCopy = {}`.

### 3.3 Part

Every part has the same 4-line shell. The registration wrapper sits *outside* the function, so
the moved body stays at exactly one tab — the same indentation as inside the monolith's IIFE —
and every moved line is byte-identical:

```js
/*
 * Visit-profit market: per-planet growing profit, the flight ledger, harvest and stay-pay,
 * predicted harvest, the universe mask.
 * not here: landing settlement → game_flight.js; contract payouts → game_contracts.js
 * Part of GravityGame (load order: PARTS in gravity_game.js).
 */
(typeof module !== 'undefined' && module.exports
	? attach => { module.exports = attach; }
	: attach => globalThis.GravityGame.part('game_market.js', attach)
)(function (GravityGame, inner) {
	'use strict';
	const { GravitySim, OrbitWorld, CAREER, MONEY, price, canPay } = inner;

	/* … moved statements, verbatim, with the comments above them … */

	Object.assign(GravityGame, { createMarket, planetProfit, harvestMode: harvestModeOf });
	Object.assign(inner, { createMarket, openFlight, walkProfitLog });
});
```

Rules:

- **Import:** one `const { … } = inner;` line — externals plus every name taken from the core or
  an earlier part. It is the part's depends list.
- **Publish:** `Object.assign(GravityGame, { … })` carries exactly the public keys this part owns
  (original key names, including the two renamed ones); `Object.assign(inner, { … })` carries
  every name another part reads, always under its **declaration name, shorthand only**. A name
  can be on both. The public object never feeds internal callers.
- **Back reference:** a call into a *later* part is written `inner.name(…)` at call time. That
  spelling marks the few genuine cycles (§4.3). A definition-time read of a later part is a bug.
- **Bot parts** keep `GravityBot.prototype.x = function (…)` verbatim (methods share through
  `this`); the public static statements (`GravityBot.LEVELS = LEVELS;`) travel with the part
  that declares the constant.
- **Hot paths:** intra-part calls stay bare closure calls; imported names are closure `const`s,
  exactly as in the monolith. Only back references are property loads, and none may sit inside
  a loop body (the tool reports any).

### 3.4 Cross-file `let` → accessor

A destructured `let` is a copy taken at attach time and silently freezes. The monolith has 29
top-level `let`s. All but these stay private to their part; these are read across parts and use
an accessor (all but two already exist):

| state | owner | other parts call |
|---|---|---|
| `harvestMode` | `game_market.js` (next to `setHarvestMode`) | `harvestModeOf()` |
| `spaceWearScale`, `padScale`, `rotScale`, `payScale` | `game_ship.js` | `spaceWearScaleOf()`, `padScaleOf()`, `rotScaleOf()`, `payScaleOf()` |
| `politics` | `game_politics.js` | `politicsOn()` |
| `specialPlanets` | `gravity_game.js` | `specialPlanetsOn()` |
| `openingTraceCount` | `game_opening.js` | **new** `openingTraces()` / `restoreOpeningTraces(n)` |
| `lastPairTracksKey`, `lastPairTracks` | `game_seat_rank.js` | **new** `cachedPairTracks(key)` / `rememberPairTracks(key, tracks)` |

The two new accessor pairs are hand edits in the monolith before the cut (stage 0), so the cut
itself stays mechanical. Shared `const` objects and typed arrays may be imported: the reference
is shared and mutation is seen by both sides. The tool refuses any cross-part write.

### 3.5 Fresh instances (`seat_search_test.js`)

The test needs a fresh module per fixture (own seat-plan and pair-track caches) and a fake clock
(`step(1)` must mean one unit; `createSeatSearch` reads `performance.now()`). Keeping its current
fixture — `vm.runInNewContext` of the core source with a `module` and `require` — would run the
parts through Node's `require`, compiled in the main realm, so `performance` would be the real
clock and the drain count nondeterministic; it could only be kept by rewriting game code for the
test. Instead the fixture switches to the browser path: a fresh `vm` context with the six
external modules as globals and `performance: { now: () => clock++ }`, then the core and its
`PARTS` evaluated in order as scripts, `context.GravityGame` as the module. That keeps the test's
meaning, needs no game-code edit, and exercises the page registration path from Node.

### 3.6 Measured side effect

The monolith's `GravityGame` has fast properties; built by `Object.assign` across parts it is a
dictionary-mode object (`%HasFastProperties` false; `GravityBot.prototype` already is today). On
`game_bench` the prototype split measured 27.0 s against 26.7 s with identical deterministic
output — noise. `career_bench` and `game_bench` wall clock stay a gate (§10).

## 8. The move tool and its audit

The cut is mechanical, never by hand. A one-shot Node tool built on `acorn` + `eslint-scope`
(installed outside the repo, `npm i --prefix /tmp/split-tool acorn eslint-scope`) takes a
monolith and an **anchor map** — per output file: its block anchors (first..last) and its named
singles; for the bot, method names — and:

1. assigns every top-level statement to exactly one file (anchor ranges, then named singles; an
   unassigned statement stays in the core, so a partial map is a valid intermediate step);
2. resolves every reference through scope analysis: same file → untouched; core or earlier part
   → added to the import line; later part → rewritten `inner.name` (shorthand properties
   expanded); a definition-time read of a later part → **refused**;
3. rewrites a cross-part read of a top-level `let` to its accessor; a cross-part `let` without
   an accessor, or any cross-part write → **refused**;
4. reports single-reader constants/scratch (rule 2) and any back reference inside a loop body;
5. splits the public literal (`const GravityGame = {…}`) and the bot's static statements by
   owner, preserving key names (`harvestMode: harvestModeOf`);
6. emits each part: header placeholder, shell, import line, statements verbatim with their
   leading comments, the two publish lines;
7. **audits**: every top-level statement of the monolith occurs verbatim in exactly one output
   file, modulo the listed `inner.` and accessor rewrites; prints counts per file, the shared
   name count, the back-reference list and the relocation list.

Headers are then written by hand (one per part). After the split lands, the tool and the final
anchor map go to `archive/0.7.53-split-tool.js` beside the archived plan, so the audit can be
re-run against the base commit; it is not kept in the live tree.

## 9. `experiments/parts_test.js` (new, fast tier)

Dependency-free, seconds. For each of `gravity_game.js`, `gravity_bot.js`, `comms_copy.js`:

- `index.html` lists the core's `PARTS` right after it, in order;
- every name on a part's `const { … } = inner;` line is published to `inner` by the core or an
  earlier part; every `inner.name` read is published by some file;
- no key is published to `inner` twice; `inner` publish lists are shorthand only (no renames);
  no public key is published twice;
- assembling through Node `require` and through the browser path (fresh `vm` context, core +
  parts as scripts) yields the same public key set and value types, with no `part` property left
  and `CommsCopy` frozen in both.

The permanent test checks structure, not a frozen key list, so later plans can add API freely;
the exact-key parity against the base commit is a one-time gate of this plan (§10).

## 11. Acceptance

- **Sizes:** no file over ~950 lines; the game and bot parts 145–750 lines; the cores ~600
  (game), ~420 (bot), ~120 (comms).
- **API parity:** `GravityGame`, `GravityBot`, `GravityBot.prototype` and `CommsCopy` have the
  base's exact key sets and value types (key order may differ); `CommsCopy` frozen; no new
  globals and no leftover own property (`part` is deleted after assembly); internal callers never go through the
  public object, so test monkeypatches reach exactly what they reached before.
- **Behaviour parity:** deterministic bench output identical to the base; fast and slow tiers
  and `dom_smoke` show the base's results check-by-check; `file://` works with no build step.
- **Move audit:** every monolith statement found verbatim in exactly one file, modulo the listed
  rewrites; back references are the listed ones.
- **Measured locality, not promised percentages.** Take the open plans (`0.7.44`, `0.7.45`,
  `0.8.0`–`0.8.8`) and ten recent archived worklog tasks; for each, list the parts whose bodies
  would change, found from `PARTS` and the pairing table without a search; record the table in
  the worklog. Expectation, from a symbol scan of the open plans against this partition: a
  focused edit (one law, one bot decision, one copy topic) is one rule part plus at most one bot
  part; a cross-cutting feature (`0.7.45` buy-ships names symbols in ~10 rule parts) stays
  multi-file — no partition makes it 1–2 files, but each file is then a single read.
