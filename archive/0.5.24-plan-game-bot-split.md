# 0.5.24 plan — split the rule set and the bot into one file per area

## Goal

`gravity_game.js` (7,847 lines, 312 kB ≈ 85k tokens) and `gravity_bot.js`
(4,855 lines, 206 kB ≈ 55k tokens) were single IIFEs. Any edit to a career
law or a bot decision meant loading most of a file to find the function, its
constants and the helpers it calls, and every agent that grepped them paid for
long hits. Split both, the way `0.5-plan-gui-split.md` split the page, so that:

- an agent finds the right file from **one table of contents** (the core's
  `PARTS` list, one comment per file), opens **one part of 140–740 lines**
  (the largest is ~28 kB ≈ 8k tokens) and edits there;
- a part's first ~15 lines say what it owns, which external modules it uses,
  and every name it takes from other parts — the `const { … } = NS;` import
  line — so a typical edit is decided without opening a second file;
- a typical edit touches one part, at most two, and never a chain.

The split is a pure move: no behaviour, API or replay change. It stays
`file://` friendly (classic scripts, no modules, no build) and runs under node
through the unchanged `require('./gravity_game.js')` / `require('./gravity_bot.js')`.

## Mechanism: one namespace object, ordered parts, destructured imports

Each part is its own IIFE. The core creates the namespace object
(`GravityGame` / `GravityBot`) and lists the parts in load order; each part

1. takes the namespace (`node ? require('./gravity_game.js') : root.GravityGame`)
   and its external modules (`GravitySim`, `OrbitWorld`, …) one line each;
2. destructures every name it uses from earlier parts in **one**
   `const { … } = GravityGame;` line — the part's depends list;
3. keeps the moved code byte-identical: inside a part every call stays bare;
4. ends with `Object.assign(GravityGame, { … })` — the part's provides list:
   every name another part or an outside caller (page, tests) reads.

A call into a **later** part cannot be destructured (it is not published yet
at load), so it is written in full: `GravityGame.checkEnded(career)`. That
form is reserved for back references and so marks them.

Node: the core assigns `module.exports` first, then `require`s each part;
a part's `require('./gravity_game.js')` is a cycle that returns the
in-progress (already assigned) object. Only the core is ever required.
Browser and the vm page stub: `index.html` lists the core, then its parts in
`PARTS` order; `experiments/dom_stub.js` discovers the list from the page.

Bot parts add methods to `GravityBot.prototype`, which already shares them
across files through `this`; only the tuning constants and the free helpers
cross files, published as statics on `GravityBot` (as some already were).

### Rejected alternatives

- **Flat global scripts** (the gui's mechanism): the 870 game and 120 bot
  top-level names would share the page's global lexical scope with the gui's
  840 — collisions are certain — and node needs one module per require.
- **`G.name` at every cross-part reference**: rewrites thousands of call
  sites (the diff is no longer reviewable as a move), turns a closure read
  into a property load on a ~420-key object in hot planning loops, and makes
  test monkeypatches (`GravityGame.startComposition = …`) reach internal
  callers that never saw them before.
- **One scope rebuilt by concatenation** (node loader evals all parts in one
  function): impossible across browser script tags without a build step.

### Mutable state never crosses a file

A destructured `let` is a copy, so a top-level `let` stays in the part that
owns it, and readers elsewhere use an accessor:

| state | owner | readers elsewhere use |
|---|---|---|
| `harvestMode` | `game_market.js` (moved next to its setter) | `harvestModeOf()` |
| `politics` | `game_politics.js` (with `setPolitics`) | `politicsOn()` |
| `specialPlanets` | `game_career.js` | `specialPlanetsOn()` (19 reads rewritten) |
| `padScale` / `rotScale` / `payScale` / `spaceWearScale` | `game_ship.js` | `padScaleOf()` / `rotScaleOf()` / `payScaleOf()` |
| `openingTraceCount` and the opening scratch | `game_opening.js` | `openingTraces()` / `restoreOpeningTraces(n)` |
| `lastPairTracksKey` / `lastPairTracks` | `game_seat_rank.js` | `cachedPairTracks(key)` / `rememberPairTracks(key, t)` |
| gift budgets, leg probe, composition scratch | their own part | not read elsewhere |

Shared `const` objects and typed arrays (scratch buffers, caches) may be
imported: the reference is shared, so mutation is seen by both sides.

## Partition

Boundaries follow areas, not line counts: a file owns every top-level
declaration of its area, contiguous where the area was contiguous; a small
helper moves to the part its users load after (`planetInMask`/`hqMask` to the
opening layer, `round2` to the core, `draw01` to the career numbers,
`colonyInPlay` to the market, `ownPart`/`topTier`/`fillLight`/`fitPad` to
building, `joinGalaxy` to the lifecycle, the evacuation fare to the ship).
The order minimises back references; 12 remain, all call-time:
`checkEnded` (×6, after a purse change), `refreshCareerMedic` (×2),
`placeShip` (arrest), `pay`/`clawbackTaskRefund` (sport → contracts) and
`GIFT` (link codec → gifts). Each is a genuine cycle between areas.

## Method

The move is mechanical and was done by a throwaway AST tool (acorn +
eslint-scope), not by hand:

1. assign every top-level statement to a part by anchor name (a part owns
   statements from its anchor to the next anchor) plus per-name overrides;
   a bare statement (a fill loop) stays with the declaration it follows;
2. rewrite cross-part reads of a `let` to its accessor and refuse any
   cross-part write;
3. resolve every reference through scope analysis: same part → untouched;
   earlier part → destructured; later part → `NS.name` (shorthand
   properties expanded); a definition-time read of a later part is refused;
4. emit each part: header, namespace and module lines, imports, the
   statements verbatim with their leading comments, provides.

Two hand edits preceded it, both in the monolith, both behaviour-preserving:
the opening trace counter and the pair-track cache got their accessors.

## Verification

- move audit: every top-level statement of both monoliths occurs verbatim in
  exactly one output file (modulo the `NS.` back references and the
  accessor reads);
- `experiments/parts_test.js` (fast tier): `index.html` lists each core's
  `PARTS` right after it in order; every import is published by an earlier
  part; no key is published twice; every `NS.name` read is published;
- the public surface is a superset: every old `GravityGame` key and every old
  `GravityBot` static and prototype method is present with the same type;
- fast and slow tiers, deterministic benches compared with the base commit,
  and one `dom_smoke` (the page script list changed).

`seat_search_test.js` evaluated the core's source in a fresh vm context to
get its own caches and a fake clock; it now evaluates the core and its parts
as browser scripts in one context.

## Rules for later edits (AGENTS.md carries them)

- find the file from `PARTS` in the core, open that part, edit there;
- a new name another part needs goes into the owner's `Object.assign` and
  the reader's import line; if the owner loads later, call `NS.name(…)`;
- a top-level `let` never crosses a file: add an accessor;
- a new part is added to `PARTS` and `index.html` together;
- never require a part directly; require the core.

## Not split, and why

`gravity_gui.js` (composer, 1.2k) already follows the 0.5 rules;
`orbit_view.js` (1.3k) and `gravity_sim.js` (1.1k) are cohesive single
subsystems edited rarely; `comms_copy.js` (2k) is copy tables read by grep;
`experiments/dom_smoke.js` (4k) and `career_bench.js` (2k) are test files whose
blocks are already run in isolation (AGENTS.md, tests).
