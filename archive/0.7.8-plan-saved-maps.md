# 0.7.8 plan — saved maps: a proven opening on disk, and an exact run state

## problem

A career page load spends almost all of its time in one place: the fair-opening
search. `prepareCareerStarts` traces candidate homes (`openingTraceHome` →
`GravitySim.routeDrain`) and ranks seamings: ~3 s of a ~3.3 s boot for a
13-world, 3-seat career in `node` on the 2-core sandbox, and ~14 s on a world
where no opening passes the fairness rule (seeds 10 and 61). A page test pays
that before its first assertion, and the same search runs again for every seed a
test or bench samples.

The search is a **pure function** of `(world seed, trade seed, universe mask,
seat count, gravity/force scales, specials on)`, and the page asks for the same
answer twice per click (the scoreboard plans, `startGame` rebuilds). A proven
answer is therefore cacheable data, not code: seed + universe + `homes` +
`targetPay` fully describe a start map.

The second ask is the player's own: save the current run and continue it later,
from an initial map or from the exact state.

## design

One data file, one logic file, one GUI area:

| file | owns |
|---|---|
| `saved_maps.js` (root, loaded first) | the registry: `root.SAVED_MAPS = [record, …]`, or `module.exports` under node. Generated by `experiments/make_saved_maps.js`, and rewritten by the game's save action |
| `saved_map.js` | `GravityMaps`: record capture, seat-plan injection, exact-state pack/unpack, `fileText`, `download` |
| `gui_maps.js` | the four buttons in the run panel, the `?map=` boot path, status text |

Load is **just the predefined file name**: `index.html` carries
`<script src="saved_maps.js">`, so a saved map is available without a picker, a
network call or a build step. Save is **append and download**: the action
appends the record to the in-memory list and downloads the whole regenerated
`saved_maps.js` (Blob + `<a download>`); dropping that file over the repo's copy
is what makes the map permanent.

### the record

```js
{
	v: 1, kind: 'start', name: 'seed 2 · 13 planets · 3 seats',
	seed: 2, universe: 13, seats: [0, 7, 6], targetPay: 2.1737928300215765,
	rule: 'career', bot: 'normal', player: 'user', cheat: null,
	rate: 1, gs: 1, fs: 1, ws: 1, ht: false,
	note: 'career default', stats: { weakest: 0.87, sites: 2 }
}
```

`kind: 'run'` adds `state`: the exact snapshot (below). Every field the page
needs to reproduce the world and the opening is present; nothing is derived at
load except the world itself (seed-driven, ~1 ms). `seats` and `targetPay` are
the search's own answer, the pay unrounded: a company that joins mid-run is
seated by its ratio to that pay (`planCareerExpansion`), so the record carries
the number the search would have left in the galaxy.

### loading a start map

1. The boot path (`?map=<index|name>`) or the `load map` button arms the record.
2. `startGame` runs with the record's seed, rule, bot level, player count,
   universe, rate and experiment scales.
3. `startCareerRun` calls `GravityMaps.applySeats(…)` **before**
   `prepareCareerStarts`; a matching record injects its plan through
   `GravityGame.rememberSeatPlan`, which fills the existing seat-plan cache
   under the same key the search would use. The search never runs.

A record is used only when seed, universe, seat count and scales match, so a
stale file cannot seat a different world.

### a start map is its seed link, minus the search

`?map=` boots the run that `?rule=career&seed=<seed>&rate=<rate>` plans for the
record's level and scales — the same captured state at boot and after any number
of frames, and the same position in the page's `Math.random` stream:

- the page's first world is built on the record's seed, as it is for `?seed=`.
  Without that pin a map boot draws one random startup seed first, which shifts
  every later helper scan and roster draw;
- the address may still say who flies YOU (`you=`, `player=`) and the orbit rate
  (`rate=`, 0.5–12), as a seed link does. Neither touches the seat plan. A seed
  link without `rate=` runs the career's default clock, which is `rate=0.5`.

What a map boot does differently: the roster size and the universe are pinned to
the record (on a seed link they follow the level and the rule until the player
changes them), the rate counts as fixed by the link, and the notice line reads
`loaded <name>` until the next notice.

A record outlives the search that proved it. `make_saved_maps.js --check`
re-plans every start record and fails when seats or pay differ, so a change to
the search cannot leave the registry — and the page tests on it — seating runs
no seed link starts.

### saving an exact state

`kind: 'run'` stores what a continuation needs, captured only while every ship
is on the ground (a flight in the air is not saved; the button says so):

- the start map fields (so `startGame` rebuilds the same world and seats);
- the trade clock and world play state: `t`, the event queue, ports, ships,
  colonies and the random stream position (`OrbitWorld.seedRandom` exposes
  `getState`/`setState` for exactly this);
- the shared market arrays, the galaxy statistics and the run counters;
- every company — purse/ledger, ship fit and condition, pads and gear, owned
  parts, prototypes, science hull, task board, launch book, contract, stats;
- each rival's turn state (gap, plan, route, burn bookkeeping) and each sim's
  visit history.

Derived data is not stored: world geometry, turret phases, `launchPads`,
`planetCount`, `planetMask` and the field are rebuilt from the seed and the
universe, and gear is stored by id (`EMC-2`, `HOLD-8`) and relinked to the
`OrbitTech` tables so item identity survives.

Restore = `startGame(record)` then overwrite the live objects in place (never
replacing `game.career`, `tradeSim` or the market, which the GUI closures hold).
The round-trip test proves it: two pages are advanced from the same state, one
continuing, one restored, and their captured states must still match after 240
frames.

## generated start maps

`experiments/make_saved_maps.js` plans seeds per configuration, keeps a seed
only when the page itself would accept its plan (`openingGroupAccepted`: no
company without a site, distinct sites, every site exitable, weakest pay ≥ 55 %
of the best) and writes `saved_maps.js`. A configuration either samples its
seeds or names them:

| universe | seats | seeds | why |
|---|---|---|---|
| 13 | 3 | 1, 2 | the career default (YOU + normal rivals) |
| 13 | 2 | 3 | YOU + one rival |
| 26 | 3 | 4 | the old default subset, three companies |
| 8 | 2 | 2 | the small universe |
| 26 | 4 | 5 | the crowded universe |
| 13 | 3 | 42, 7, 3, 520383 | the career default on the worlds the page tests are written against |

Ten records, 4.3 KB in total. A sampled seed is the first accepted one from an
offset (`from` in `CONFIGS`), not from 1: a per-config fresh start otherwise
picks seed 1 every time, because the first world is the first one that passes.
New configurations go last, because `?map=<index>` counts from the top; for the
same reason a configuration that comes up short — a named seed with no accepted
plan, too few sampled ones — fails the script and leaves the file as it is. The
registry is also the pool `load map` draws from, so it holds fair openings only:
seeds 10 and 61 have none and stay seed links.

## tests

- `experiments/saved_map_test.js` (fast tier, ~10 s): every record is well-formed
  and seats a career whose plan passes the fairness rule; `fileText` reloads to
  the same records and the committed `saved_maps.js` is exactly that text; a page
  booted on `?map=0` is seated from the record (a record with its seats reversed
  seats the run reversed) and is the run its seed link plans — equal captured
  state at boot and after a flown flight, equal next `Math.random()`; `rate=` in
  the address sets the orbit rate and changes nothing else in that state; a run
  captured at rest and restored into a fresh page continues identically for 240
  frames (purse, clock and every captured array).
- `node experiments/make_saved_maps.js --check` (slow tier, ~22 s): every start
  record is still the plan the search returns.
- `dom_smoke` once when `index.html`, the boot path or the maps group changes: it
  checks the registry, the record shape and the six map elements.
- Page tests whose subject is not the opening search boot the saved map of their
  seed through `mapSearch(seed)` in `experiments/dom_stub.js` (~0.2 s) and add
  `&rate=0.5` where the seed link carried no `rate=`.

### what an exact save has to carry

Capturing only the world is not enough: a restore then looks identical and
drifts 40 clock steps later. The page itself holds state that decides the *next*
frame:

- the sim's flight status, trail, origin and end reason (`relocate` resets all of
  it to "parked on the pad", but a career at rest sits on `STATUS_ENDED` with the
  trail of the flight it just finished);
- the bot's YOU-as-bot turn state (`bot.careerPlayer`: the plan it already made,
  its `readyStep` and the gap counters) — without it the bot re-plans on the
  first frame and queues its turret shot ~400 steps later than the live run;
- the leftover step accumulator (`playAcc`) and `playerBotSyncNeeded`, so the
  restored page does not replay the current frame.

All four are in the record (`planner`, `page`, plus the ship keys) and the
round trip is exact.

## scope boundary

No new map generator, no change to the fairness law or to the seat search: a
saved map is what the current search already accepted. Exact saves cover a run
at rest; a flight in progress, a queued turret shot and a replay are not
snapshotted (the save button refuses while flying). Rival AI is restored from
its live turn state, not from its history log.
