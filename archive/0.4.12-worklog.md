## Design & Implementation

### 1. Directional frontier (`orbit_science.js`)

- `FRONTIER[family][axis] = { below, above }` is one flat balance table. It
  weights one RU of overshoot past the family's researched range. Engine mass
  is `↓×3.00 / ↑×0.20` (light is hard), catapult efficiency
  `↓×0.30 / ↑×2.50` (high is hard); thrust and rail force are moderately hard
  upwards and cheap downwards. Families/axes not listed keep plain hull
  pricing, so the early benches and any future family need no config.
- `rangeHull(hull, family)` is the per-axis min/max of the discovered points,
  computed on demand (no cached state to go stale) and exported for the panel.
  `frontierWork` converts the overshoot to RU with `METRIC_SCALE` before
  weighting, so the difficulty is in deliberate invention steps, not kN/tonnes.
- **The frontier is additive, not a replacement.** `fee = base + k·tier·(dist
  + frontier)`. Inside the hull it is exactly the base fee (short circuit);
  outside the hull but inside the researched range it is the old `k·dist`; both
  terms add past the range. This keeps the volume-shaped cost calculation the
  draft likes while making one direction dearer.
- `previewHull` now returns `frontier` alongside `inside`/`dist`/`cost`. The
  game transaction (`researchCost`, `researchPoint`) needed no change: it
  already pays and deducts `previewHull().cost`, and accepting a point grows
  both the hull and the range.

### 2. Panel (`gravity_gui.js`, `style.css`)

- Dashed `.sciRange` box on the cost surface marks the researched range; the
  legend names it. The surface colours come from `researchCost`, so they show
  the frontier surcharge automatically.
- Readout: `outside · dist 1.073 RU · frontier +1.50 RU · fee 17.44`. A second
  metric line prints the family's `↓×… ↑×…` knobs. Both lines are family-level,
  so slider drags still only patch the readout / draft / accept button.
- `copy knobs` (§11 balance tooling) writes
  `frontier: ENGINE { thrust: { below: 0.20, above: 0.90 }, … }` plus the
  metric line to the clipboard, or shows it in the drawer notice on `file://`.
  It is dispatched before the career-over gate, like the shop `copy` buttons.
- `.sciKnobsRow` wraps the long frontier line with the button on the 390 px
  drawer; the legend's fourth span wraps under `sciPlotLegend`.

### 3. §14 career captions (`photos/prompts.md`, generator, docs)

- Three MOSS-Image captions (80–200 words, medium + subject first, positional
  layout, lighting/palette, no quality keywords): `catapult` launch rail,
  `delivery` gantry unload, `sport` orbital timing gate. They use `career` as
  the parseable situation and target `photos/career/<scene>.jpg`.
- `comfy_queue.py`: `CAPTION_ROW` accepts `career`, `--situation career` filters
  it, `target_path` already derives the folder from the target path, and
  `make_jobs` emits **one** job per career caption even with `--variants 2/3`
  because `photo_deck.js` reads no career variants. Planet variant behaviour is
  unchanged. `photos/career/.gitkeep` holds the folder; `__pycache__/` and
  `*.pyc` are now ignored.
- `photos/README.md`, README.md and the active plan §10/§14/§15/§16 are updated
  as the final spec (plan remains a reimplementation artifact, not a log).
