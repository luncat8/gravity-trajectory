# 0.7.2 plan — ship condition, wear and repair

Standalone spec: a fork can rebuild this from this file alone. Source note:
`drafts/career-economy.md` §ship maintenance cost:

	represent ship condition (storyline: repair, service, oxygen, food, …) as one parameter ~ cost: wear 0.01/s in space + 0.1 per landing + 0.1×EMC acceleration for the starter ship; upgrades/science reduce wear. limits lucky starts (observation device fail, preventing earn huge amount of money in case of very long route occasionally found).
	at 0: observation device fails (visits pay nothing); ship can't launch EMC and use IMP engine.
	repair button near (before) launch btn; 2 cr per 1 condition.
	replace launch button with btn with dropdown:
	- repair & launch (total cost)
	from dropdown triangle available separate:
	- repair
	- launch (as current button)
	numbers subject to balance; space weather affects wear.

Depends on `0.7.1` for the unit contract: wear is priced per **sim second**
(`GravitySim.simSeconds`), never per world minute or year. `0.7.3` reuses the
per-ship record for bought ships.

`0.7.1` does not change the pace (§2.9 answered: today's `×4` is renamed `×1`,
physics untouched), so `WEAR_SPACE = 0.01` stays “per sim second” and a `100 s`
flight still costs `1.0`. If that rename ever turns into a real 1:1 clock
instead, the constant is re-derived here, not before.

## 1. the parameter

One number per ship:

	career.ship.condition   0…1, 1 = new
	career.ship.condition   displayed as Math.round(condition * 100) + ' %'

- `createCareer` starts at 1; `startCareer` resets it to 1 (a fresh company
  gets a fresh ship); `resetCareer` clears it.
- It is a **ship** field, not a company field: `0.7.3` gives every bought ship
  its own `condition` and `career.wearScale` (1 flagship, 2 fleet).
- The observation device remains the existing `career.ship.obs` record. A
  condition of 0 does not remove the part; it makes it report nothing.
- `career.wearScale = 1` for the flagship; `2` for a bought ship in `0.7.3`.

The existing `career.ledger.reports` flag is the company's single-ship report
flag today (`refitShip` writes it). In this plan it becomes
`career.ship.obs.fitted && career.ship.condition > 0`; `0.7.3` moves the flag to
the ship/sim because one ledger will then serve several ships (see §9).

## 2. the wear law

All constants in `gravity_game.js`, one block, no per-frame allocation:

	WEAR_SPACE       = 0.01   // condition per sim second in flight
	WEAR_LANDING     = 0.1    // per landing
	WEAR_EMC         = 0.1    // at WEAR_EMC_REF acceleration
	WEAR_EMC_REF     = 2.0    // m/s², the fragile-load reference
	WEAR_IMP         = 0.1    // per WEAR_IMP_DV of impulse
	WEAR_IMP_DV      = 200    // px/s of Δv
	WEAR_FLEET       = 2      // non-flagship multiplier (0.7.3)
	WEAR_SCIENCE_MIN = 0.5
	WEAR_SCIENCE_STEP = 0.02  // per accepted research point
	WEAR_REPAIR_COST = 2      // cr for a full 1.0 of condition

The per-ship factor:

	wearFactor(career) =
		career.wearScale *
		max(WEAR_SCIENCE_MIN, 1 - WEAR_SCIENCE_STEP * career.research)

`career.research` counts accepted science points, so a company that has done
twenty inventions wears at 0.6 of the starter rate. This is the v1 “science
reduces wear”; a future `hull`/materials science family can replace the second
term without touching the wear law. The `OBS` tier does not change wear in v1
(there is only one fitted device).

### while flying

`careerAdvance(career, rate, steps)` is already called once per career per
step (the page for the human, `stepCareer` for every rival). Add:

	if (career.flying) {
		setShipCondition(career, career.ship.condition -
			WEAR_SPACE * GravitySim.simSeconds(steps, rate) * wearFactor(career));
	}

`career.flying` is set true in `careerBeginFlight` and false in
`careerEndFlight`. Landing, pad waits and a paused clock do not wear the ship:
the draft says “in space”, and a wait is pad time.

### at launch (EMC)

Add `OrbitTech.launchAccel(speed) = speed * speed / (2 * RAIL_M)` (the same
acceleration the fragile-load rule already uses). In `careerBeginFlight`,
after the fee and energy are settled:

	const accel = OrbitTech.launchAccel(sim.speed);
	setShipCondition(career, career.ship.condition -
		Math.min(0.5, WEAR_EMC * (accel / WEAR_EMC_REF) * wearFactor(career)));

A 100 px/s starter launch is 1.79 m/s² → 0.089 wear; a 200 px/s launch is
7.14 m/s² → 0.357. Cap the single-launch wear at 0.5 so a very fast rail cannot
zero a new ship in one shot. Apply it in `careerBeginFlight`, which both the
human `fire()` and the rival `careerLaunch` use, so every company pays it once.

### landing

In `careerEndFlight`, only when `sim.endReason === END_IMPACT` and
`sim.endBody >= 0`, **after** `settleLanding` so the landing that used the last
0.05 still reports:

	setShipCondition(career, career.ship.condition -
		WEAR_LANDING * wearFactor(career));

An exit, timeout or abort is not a landing; the flight wear already ran. The
ship can land at condition 0; it is stranded only in the launch sense.

### impulse

In `careerBurn`, after `sim.burn` succeeds and the fuel is spent:

	const usedDv = dv;
	setShipCondition(career, career.ship.condition -
		WEAR_IMP * (usedDv / WEAR_IMP_DV) * wearFactor(career));

A 200 px/s rescue burn costs 0.1; a full 320 px/s burn 0.16. Proportional to
delivered Δv, not to fuel mass, so a heavy tank is not punished twice. The
draft's “0.1×EMC acceleration” is the EMC term; this is the equivalent impulse
term. No wear is charged for a refused burn.

### space weather

One hook, no zones in this plan:

	careerWearAt(career, x, y) → multiplier, default 1

The flight loop passes the live cargo position (`sim.cargo.x/y`); a later
space-weather plan replaces the default with the weather field. `careerAdvance`
has no position, so the multiplier is applied by the caller:

- the page, after `cargoSim.stepOne()`, calls
  `GravityGame.careerWeatherWear(career, cargoSim)`;
- `stepCareer` does the same for each rival after `stepOne`;
- landing wear uses the endpoint multiplier once.

Until weather exists the function returns 1 and allocates nothing.

### floor, rounding and the one setter

Every condition write goes through one setter, so the report flag can never be
stale:

	setShipCondition(career, value) {
		career.ship.condition = value < 0 ? 0 : value > 1 ? 1 : value;
		career.ledger.reports = career.ship.obs.fitted &&
			career.ship.condition > 0;
	}

`careerAdvance`, `careerBeginFlight`, `careerEndFlight`, `careerBurn` and
`repairCareer` call it; no caller does `condition -=` directly. This matters
in flight: a ship that wears to 0 between two harvests must stop paying at the
next visit, not only after the next refit.

Do not round the stored value; round only for display and for the repair price
(`Math.round(cost * 100) / 100`). A 0.001 residue must not make a launch
illegal after a repair to 1.

## 3. what condition 0 means

Three gates, all in one helper so the UI and the bot cannot disagree:

	careerShipUsable(career) = career.ship.condition > 0

- **Visits pay nothing.** `refitShip` (and every condition write) sets
  `career.ledger.reports = career.ship.obs.fitted && careerShipUsable(career)`.
  `visitReports` already refuses a visit when `ledger.reports` is false, so
  harvest, rot clearing, bribe windows and `estimateProfit` all follow.
- **No EMC launch.** `railBlock(career, sim, planet, speed)` returns
  `'ship worn out — repair before launch'` when `!careerShipUsable(career)`.
  That blocks own pads, commercial, Capital, rebel and rival rails through the
  one function the button and the bot both call. `evacuate` is not an EMC
  launch and stays available; it is the only way home from a planet with no
  repair money.
- **No impulse.** `careerBurn` returns false when `!careerShipUsable(career)`.
  The aim HUD disables the burn arm through `canImpulse()`, and the button
  says `repair needed` rather than offering a burn that will be refused.

`canImpulse()` in `gui_aim.js` reads `career.ship.condition` next to the engine
and fuel checks. `careerDeparture` (the bot's physical exit gate) returns
`out.ok = false`, `out.reason = 'ship worn out'` at 0 so the rival planner
repairs instead of repeatedly proving an impossible exit.

## 4. repair

	repairCost(career) = WEAR_REPAIR_COST * (1 - career.ship.condition)
	                     // 0 at 1, 2.00 at 0; communism makes it 0

- Full repair only. A partial repair would make the button a slider; the draft
  asks for one price per condition point, and 2 cr is small enough that a
  split is not useful. `repairCareer(career)`:
  - refuses at `condition >= 1`, `ended !== CAREER_OPEN`, or purse < cost;
  - subtracts `price(career, cost)` (so `communism` is free);
  - sets `condition = 1`, `career.repairs += 1`, `career.maintenanceSpent += cost`;
  - calls `refitShip(career)` (which re-syncs `ledger.reports`) and
    `checkEnded(career)`;
  - returns true, so a caller can chain a launch.
- **Where:** anywhere the ship is landed, including a padless planet, a
  commercial world, a rival pad or the Capital. A repair is a service, not a
  claim; restricting it to HQ would turn a dead ship on a padless rock into a
  pure evacuation fee with no choice. This is the one location decision; it is
  cheap to revisit if a “shipyard” building appears later.
- `createCareer` gains `ship.condition = 1`, `maintenanceSpent = 0` and
  `repairs = 0`; `careerStats.running` includes `career.maintenanceSpent`, and
  `careerStats.property` does not (a repair is consumed, not owned).
- `gui_career.careerAct` gains `act === 'repair'` → `careerRepair()`; it uses
  `activeCareer()` (the selected player's company), not always the human, so a
  bot-controlled YOU can be repaired by hand while paused.
- The shop/board header shows `condition 72 % · repair 0.56` and a `repair`
  button whenever landed and below 1.

## 5. the launch control

The existing single `#launch` button becomes a two-part control. Keep the
existing id and click handler so every test and keyboard path still finds the
launch:

	<div id="launchGroup">
		<button id="launch">launch</button>
		<button id="launchMenuBtn" aria-label="launch options">▾</button>
		<div id="launchMenu" hidden>
			<button id="launchRepair">repair · 0.56</button>
			<button id="launchOnly">launch</button>
		</div>
	</div>

- `#launch` is the main action. `#launchMenuBtn` toggles `#launchMenu`;
  `#launchRepair` calls `careerAct({ act: 'repair' })`; `#launchOnly` calls
  `launchShot()`.
- `setLaunchState` owns the labels. When `careerRule()` and the ship is landed:
  - `condition >= 1`: `launch`; menu `repair` hidden or disabled.
  - `0 < condition < 1` and a shot is armed: `repair & launch · <total>`,
    where total = repair cost + the numeric launch price (`launchFee` or own
    pad energy), formatted by the same `costText` helper. The menu offers
    `repair · <cost>` and `launch`.
  - `0 < condition < 1` and no shot is armed: `repair · <cost>`; the menu's
    `launch` is disabled until an aim exists.
  - `condition == 0`: `repair · 2.00` (or `repair & launch` once the repair
    makes the shot legal); `launch` is disabled and titled
    `ship worn out — repair before launch`.
- The click on `#launch` (`launchShot`) checks `condition < 1` first:
  - if the shot can fire (`armed`, `canAimFrom`, `careerCanFire`) and the
    repair is affordable, call `repairCareer` then continue the existing queue
    path; the launch and repair are atomic — if the repair fails, nothing is
    queued;
  - if the shot cannot fire, repair only and return;
  - at `condition == 1`, behave exactly as today.
- The dropdown is a plain `hidden` div, positioned by existing CSS; no
  allocation in `setLaunchState`. Its text changes only when the price or
  condition changes (the existing `launchState`/`launchNote` key already
  includes the label; add the rounded condition and repair cents to the key).
- Keyboard: `Enter` triggers `#launch`; `Esc` closes the menu before it
  cancels a turret queue. The menu buttons are normal tab stops.
- The `planetActionsEl` row (`buy EMC-1`, `commercial`, `evacuate`) keeps its
  place; repair appears before the launch group, not inside the planet row.

## 6. readouts

- `gui_hud_text`: the launch group's title names `condition 72 % · repair
  0.56`; the `careerPadNote` line adds ` · cond 72 %` on the pad row.
- `gui_flight`: the flight panel's device line becomes
  `OBS-1 · cond 72 %` (or `none · visits pay 0`); the existing report line is
  the place, not a new row.
- `gui_shop`: header `condition` and `repair` next to `buyFuel`.
- `careerNotice` on repair: `repaired · −0.56 · condition 100 %`.
- At 0, the notice on a blocked launch: `ship worn out · repair 2.00 · visits
  pay nothing until repaired`.

## 7. rivals

`stepCareer` already calls `careerAdvance` for every company; `careerBeginFlight`
and `careerEndFlight` are the same functions the rival launcher/landing uses.
So wear and the 0 gates apply to every company with no separate path.

Between flights, `careerBetweenFlights` gets a repair priority **before**
expansion and gear:

	if (career.ship.condition <= CAREER_REPAIR_AT &&
		career.ledger.purse + 1e-9 >= repairCost(career) + CAREER_PURSE_RESERVE) {
		repairCareer(career);
		actions += 1;
	}

`CAREER_REPAIR_AT = 0.7` (a rival services early, so it rarely reaches 0).
At exactly 0 the repair ignores the reserve if that is the only way to fly;
otherwise the company evacuates (if it can afford the fee) or is restarted by
the existing broke path. Add the repair cost to the expansion reserve so a
company cannot spend its last 2 cr on a rail and strand itself.

`careerRestart` starts a fresh ship at condition 1 via `startCareer`.

## 8. tests

New `experiments/career_wear_test.js`, no browser:

1. **Space:** a career in flight for `100 s` at rate 1 loses `1.0` condition;
   a 30 s flight loses `0.3`; no wear while landed.
2. **Landing:** an `END_IMPACT` costs 0.1; `END_EXIT`, `END_TIME` and
   `END_ABORT` cost no landing wear.
3. **EMC:** a 100 px/s launch costs `0.089`; a 200 px/s launch `0.357`; the
   single-launch cap holds.
4. **Impulse:** a 200 px/s burn costs 0.1; a refused burn costs 0.
5. **Science:** 20 accepted points make the same flight cost 0.6 of the base;
   the floor is 0.5.
6. **Zero gates:** at 0, `careerCanFire`/`railBlock` refuses every pad type,
   `careerBurn` refuses, `ledger.reports` is false and `harvestPlanet` pays 0;
   `evacuate` still works.
7. **Repair:** from 0 costs exactly 2.00 and sets 1; from 0.5 costs 1.00;
   `communism` costs 0; no double charge at 1; `maintenanceSpent` matches.
8. **All companies:** a rival that flies and lands has the same condition
   arithmetic; `careerBetweenFlights` repairs at 0.7 when it can afford it.
9. **No allocation:** the frame path adds no object; `careerAdvance` only
   arithmetic.

`obs_test` changes: `ledger.reports` now follows condition as well as the
fitted part. `career_bench` known lines change because wear eventually blocks a
long bot run; add a `STATS=1` line for `repaired`/`maintenance` and re-baseline
with a named seed, not by loosening the checks.

`dom_smoke`: `#launchGroup`, `#launchMenuBtn`, `#launchRepair`, `#launchOnly`
exist; at condition 0.5 the main label starts `repair & launch`; the menu
repairs and the label becomes `launch`; at 0 the main label is `repair` and
`#launch` is disabled.

## 9. hand-off to 0.7.3

A bought ship shares its owner's `ledger`, so `ledger.reports` cannot stay a
single company flag: one dead ship would silence a live one. Before fleet
ships fly, move the report test to the ship:

- `visitReports(ledger, market, planet, reports)` takes the ship's flag;
  `stepHarvest` reads `sim.reports`; `harvestPlanet` takes the flag;
- `estimateProfit`/`estimateProfitLog` take an optional `reports` (default
  true) and the aim readout passes `activeCareerShip().reports`;
- `refitShip` writes `career.ship.reports`, not `career.ledger.reports`.

This plan keeps the single-ship path working; the move is mechanical and is
listed again in `0.7.3`.

## scope boundary

No space-weather zones, no jammer, no new science family, no fleet here. No
condition-driven part removal (the OBS part stays fitted). No partial repair.
No change to launch fees, harvest values, research costs or politics. Rival
companies wear and repair; they do not buy fleets in this plan.
