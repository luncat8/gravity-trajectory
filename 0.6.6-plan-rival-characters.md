# 0.6.6 plan — rival characters: four companies that want different things

Standalone spec: a fork can rebuild this from this file alone. Source notes:
`drafts/rivals-competitions.md` §5.1 and `drafts/bots-and-tools.md` §8.1.
Depends on `0.5.16-plan-rival-first-shop.md` (the opening purchase) and on the
competition plan (`0.6.4`), because one of the four characters is a racer.

## problem

Every rival is the same company with the same weights. The draft asks for four
preferences — *capture and build*, *quests*, *rocket engine*, *competitions* —
and the 0.5.21 benches show why it matters: the opening shop decides whether a
company can use the board at all, and a company that never buys a hold is
invisible to half the game. One weight table that every rival shares is also why
`career_gravity_bench` totals move as one block when any single policy changes.

## shape: a character is data, not a controller

Do not fork `careerPlan`. The controller already ranks candidates by a score
built from a small number of terms (payload, pads, science, quest progress,
burn). A character is **a row of weights** over those terms:

\tconst CAREER_CHARACTERS = [
\t\t{ id: 'builder',   pads: 1.6, quest: 0.8, burn: 0.6, sport: 0.6, science: 1.0 },
\t\t{ id: 'emissary',  pads: 0.7, quest: 1.8, burn: 0.8, sport: 0.6, science: 0.9 },
\t\t{ id: 'rocketeer', pads: 0.8, quest: 0.8, burn: 1.8, sport: 0.8, science: 1.3 },
\t\t{ id: 'racer',     pads: 0.7, quest: 0.7, burn: 0.9, sport: 2.0, science: 0.8 }
\t];

- The weights multiply the **existing** term values in `careerScoreFacts` /
  `careerScoreTail`; no new term is invented, so a character can only re-rank
  the same candidates. That keeps the search, the slicing and the determinism
  untouched — the one property a bench can rely on.
- The character is drawn per company from the run seed (`hashBits(seed, index,
  SALT_CHARACTER)`) unless `?chars=builder,emissary,…` pins it, so a replay
  reproduces the same cast.
- The HUD's score row title names the character (`R1 · emissary`), and the bot
  log's first line prints the weight row, so a bench failure can be attributed.
- The opening shop reads the character: `builder` weighs a pad claim, `emissary`
  weighs a hold first (that is the 0.5.16 varA change, finally *justified* by a
  character rather than applied to everyone), `rocketeer` buys the tank and
  engine, `racer` buys the lightest ship and enters races.

## what each character must be able to show

| character | the measurable it exists for | bench column |
|---|---|---|
| builder | pads claimed per world hour | `pads` |
| emissary | contracts accepted and completed | `quests` |
| rocketeer | burns fired and rescued flights | `burns`, `rescues` |
| racer | competitions entered and won | `races` |

`career_gravity_bench` already prints `pads`; the other three columns are one
counter each on the bot (the same way `careerBuilds` is one), so the bench gains
four numbers and no new bench.

## Validation

- On seeds 1-12 at 1200 s, each character is **the best in its own column** on
  at least 8 of 12 seeds (a character that is never best is not a character;
  a character that is best at everything is a weight bug).
- `hard` still beats `easy` on money on the same seeds (0.4.27's ladder is a
  controller-skill test and must not be confused with a character test).
- Determinism: the same seed and the same character set reproduce the same
  cast, the same openings and the same bench totals; a replay link re-flies a
  bot-flown YOU with the same character.
- `career_bench`, `career_bot_bench` known failures may grow only by names that
  the character changes explain, and the worklog must list them.
- No frame-budget regression: the weight multiply is four number multiplications
  per scored candidate; `career_bot_bench`'s slice timing must stay inside its
  budget.

## order

1. **Weights only**, one bench run: does a character move its own column at all?
2. **The opening shop** reads the character (this supersedes 0.5.16's global
   change: the same edit, but applied per company).
3. **`racer`** last, because it needs `0.6.4`'s competitions to exist.

## Scope boundary

No change to the flight controller's search, no new candidate generator, no
per-character physics, and nothing that changes what a *human* player can do.
A character is a preference over the same legal actions.
