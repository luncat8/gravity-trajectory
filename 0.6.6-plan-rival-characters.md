# 0.6.6 plan — rival characters: four companies that want different things

Standalone spec: a fork can rebuild this from this file alone. Source notes:
`drafts/rivals-competitions.md` §5.1 (`implement bot character that prefer …`),
`drafts/bots-and-tools.md` §8.1 (`update bot to be compete.`) and the
«decide based on the bot’s personality» sentence of
`drafts/politics-quests.md` §3.1. The fourth character needs the competitions of
`0.6.4-plan-competitions.md`.

## problem

Every rival is the same company with the same numbers. The draft asks for four
preferences — *capture planet and build facilities*, *quest take and solve*,
*use rocket engine*, *participate competitions and have good ship for it* — and
today the only thing that differs between two rivals is one seeded yes/no
(`careerBribeProne`: half of them never take a bribe). One shared policy is also
why the totals of `career_gravity_bench` move as one block when any single
constant changes.

## what every rival keeps

The opening is not a character trait. Every rival buys `HOLD-8` as its first
purchase wherever it stands (`careerBetweenFlights`); without a hold a company
cannot accept a delivery or a medical mission, and making that purchase
unconditional was worth `+3.07 ± 2.02` purse per rival-game (30 seeds, 1200 s).
A character changes what is bought **after** that, never whether it happens.

## shape: a character is one row of data, read where the controller already decides

Do not fork `careerPlan`. The controller makes five kinds of decision, each in
one function, and each already turns on a constant. A character is a row that
scales those constants:

	const CAREER_CHARACTERS = [
		{ id: 'builder',   pads: 1.6, quest: 0.8, burn: 1.0, sport: 0.5, bribe: 0 },
		{ id: 'emissary',  pads: 0.7, quest: 1.8, burn: 1.0, sport: 0.5, bribe: 0 },
		{ id: 'rocketeer', pads: 0.8, quest: 0.9, burn: 0.4, sport: 0.8, bribe: 1 },
		{ id: 'racer',     pads: 0.7, quest: 0.7, burn: 0.7, sport: 2.0, bribe: 1 }
	];

| column | decision, function | what it scales today |
|---|---|---|
| `pads` | the shot score, `careerScoreFacts` | `padValue` (a new site, an own pad, the network) |
| `quest` | the shot score and the board, `careerScoreFacts`, `careerAccept` | `careerEval.credit` (the open leg) and the accept score of a contract |
| `burn` | the mid-flight burn, `careerBurnScore` | `careerBurnGain`, the gain a burn must beat the coast by — below 1 burns more readily |
| `sport` | the board, `careerAccept` | the accept score of a `TASK_COMPETE` offer |
| `bribe` | the rulers' money, `careerBribe` | replaces the seeded `career.bribeProne` yes/no |

- A weight multiplies a value the function already computes; no new term and no
  new candidate. A character can only re-rank the same legal actions, so the
  search, its slicing and its determinism are untouched.
- The shop reads the same row for its order after the hold
  (`careerBetweenFlights`, `careerPadGear`, `careerResearch`): `builder` buys pad
  gear before ship parts, `emissary` the bigger hold, `rocketeer` the engine and
  the tank, `racer` the engine and nothing else that adds mass — the note's
  «good ship for it».
- The cast is drawn where the bribe persona is drawn now (`startCareers` in
  `gravity_bot.js`), from `GravityGame.rivalSeed(seed, index)` with its own salt,
  unless `?chars=builder,emissary,…` pins it (`gui_share.js`). The same seed gives
  the same cast.
- The scoreboard row's title names the character (`R1 · emissary`) and the bot
  log's first line prints the row, so a bench result can be attributed.

## what each character must be able to show

| character | the measurable it exists for | bench column |
|---|---|---|
| builder | pads claimed per world hour | `pads` |
| emissary | contracts accepted and completed | `quests` |
| rocketeer | burns fired, and flights saved by one | `burns`, `rescues` |
| racer | competitions entered and won | `races` |

`career_gravity_bench` already prints `pads`; the other columns are one counter
each on the bot (the way `careerBuilds` is one), so the bench gains four numbers
and no new bench. Purse per company comes from the `STATS=1` table of
`0.6.10-plan-map-statistics.md` when it exists.

## order

1. **Weights only**, with the cast pinned to four of one kind and then to one of
   each: does a character move its own column at all?
2. **The shop order** after the hold.
3. **`racer`** last, because it needs `0.6.4`'s competitions to exist. Until then
   the cast is drawn from the first three.

## Validation

- On seeds 1-12 at 1200 s, each character is **the best in its own column** on
  at least 8 of 12 seeds (a character that is never best is not a character; a
  character that is best at everything is a weight bug).
- No character ends poorer than today's rival by more than the paired noise:
  `PAIRED=1` purse per rival-game against the uniform cast, same seeds.
- `hard` still beats `easy` on the same seeds (`0.4.27-plan-bot-balancing.md` is
  a controller-skill test and must not be confused with a character test).
- Determinism: the same seed and the same `?chars=` reproduce the same cast, the
  same openings and the same bench totals.
- `career_bench`, `career_bot_bench` known failures may grow only by names that
  the character changes explain, listed in the worklog.
- No frame-budget regression: a weight is one multiplication per scored
  candidate; `career_bot_bench`'s slice timing stays inside its budget.

## Scope boundary

No change to the flight controller's search, no new candidate generator, no
per-character physics, and nothing that changes what a *human* player can do.
A character is a preference over the same legal actions.
